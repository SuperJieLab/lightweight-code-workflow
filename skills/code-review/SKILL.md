# 复核 —— 两层，各有各的对照物

> 层一的对照物是**语言规范**，层二的对照物是**plan**。两者不能合并：一个查「代码本身有没有病」，一个查「这次实现有没有兑现方案」。
> 层二发现不了 plan 本身的错——它的对照物就是 plan。别在这里声称「结构也审过了」。

## 输入与依赖

**前置状态**：plan 的 `status` 为 `done`。

**开工先读**：

- plan 全文，其中「实现方式与取舍」「落地拆解」两节与修正记录是层二的对照物。
- 本次 diff 的完整范围。
- `dev/RULES.md` —— 测试框架、测试文件位置、验证命令以它为准；有目录承诺表时一并读，层二判「归属是否与表一致」要用它当基准。

## 流程

### 层一：语言机制

对照 `references/lang-checklist.md`，查并发、内存、边界、错误处理、性能。与需求无关，只看本次 diff 的可达路径。

**两条实现路径：**

- **默认（无外部依赖）**：按清单人工/模型逐项过 diff。报告里的行号用引用反推：

  ```bash
  python3 <本 skill 目录>/scripts/locate.py <目标文件> <片段文件>
  # 或：cat snippet.txt | python3 .../locate.py <目标文件> -
  ```

  先让审查者写出**原文引用**，再由脚本钉行号。**不要让模型直接报行号**——那是必错的猜测，而且错得很像对的。

- **增强（可选）**：如果环境里装了 open-code-review 的 CLI（`ocr`），可以把它当额外的候选生成器跑一遍。它不替代层一，只是多一路来源。没装就跳过，**不影响流程完整性**——默认路径不能有外部依赖。

**层一的产物判据**：每条发现四要素齐全（文件:行号、类别与等级、一句话结论、被哪一行证伪或证实）。指不到具体行的，补取证或不报。

### 层二：方案符合性

**必须派一个独立的只读子代理**，把 diff、plan 全文、修正记录交给它，指令它只读、不修改任何东西。**不带实现阶段的会话上下文**——这正是它比实现者自审强的地方。

审七个维度：

| 维度 | 找什么 |
|---|---|
| 方案符合性 | 是否偏离 plan「实现方式与取舍」「落地拆解」的决定；偏离处修正记录里有没有 |
| 契约符合性 | plan 定义的边界是否被两端一致遵守；有没有单方面的新用法 |
| 归属一致性 | 两问：一、diff 里每个新增或改动的导出符号，是否都在归属表里、位置与表一致；二、plan 2.4 判为「应搬」的归属，diff 里是否真的搬了、搬的是整个功能还是半个，搬迁与内容修改是否分开提交 |
| 判据覆盖 | plan 判据表里每条是否真的被执行过；有没有漏跑、跑过但没留痕 |
| 异常处置 | plan「实现方式与取舍」列的退出条件与约束，代码里是否真的有对应处置，还是只写在纸上 |
| 测试质量 | 测试是否只在约定的接缝上；有无实现耦合（mock 内部）、同义反复（期望值与代码同源） |
| 简化机会 | 明显的多余抽象、死代码、可合并的分支 —— **只报告，不顺手改** |

**不审**：与本次 diff 无关的既有问题、风格偏好、措辞。

### 定级与处置

层一的发现也按这三级定，不用另一套（如 `critical` / `high` / `medium`）。

| 级别 | 含义 | 处置 |
|---|---|---|
| **Critical** | 违反契约、判据造假、异常无处置、数据错误风险 | **阻塞**，必须修复后**换一个新子代理**重审 |
| **Major** | 偏离方案决定且无修正记录、测试耦合实现 | 应修；不修须写明理由——层二写进 plan 修正记录，层一写进报告 |
| **Minor** | 简化机会、可读性建议 | 登记，不阻塞 |

层一的 Major 指「会走进错误路径但尚未造成数据错误」的缺陷：边界漏判、错误被吞掉、超时未设。层二的 Major 是「偏离方案且无记录」、「测试耦合实现」，以及**搬迁落成的三种变形**：应搬而未搬、只搬了半个功能、搬迁与内容修改混在同一次提交——第三种最危险，它让「行为有没有变」在 diff 里看不出来，回滚也拆不开。

同一次提交里既有搬运又有内容修改时，按 `git diff -M` 的相似度先判是不是纯 rename；相似度不足 100% 的，要求拆分后重审，不在一次提交里同时接受两类改动。

Critical 修复后换代理，不用原来那个——避免它为自己的报告辩护。

## 产出

一份 `checks/YYYY-MM-DD-review.md`，两段：层一发现、层二发现，各自分级。写完即固定，**不回填**（快照记的是当时发生什么）。

## 退出判据

两条同时成立：

1. 层一没有未处置的 Critical / Major；
2. 层二无 Critical，Major 不修的有书面理由（写在 plan 修正记录里）。

然后把 plan 的 `status` 改成 `reviewed`，跑 `workspace-status` 拿下一步。

## 不做的事

- **不查需求正确性**。这里没有 spec 的对照物，判不了「做的是不是要的」。
- **不查冗余**。判断「还有没有人用」要扫全库调用点，单位是整库，不在本次 diff 的范围内。
- **不改代码**。发现问题写进报告，改由执行者做；审查者顺手改会让「审的人」和「改的人」变成同一个。
- **不报无法证伪的项**。「我觉得这里不太好」不是发现。
- **不因「我觉得没问题」放过内存安全、并发、行为兼容性这三类候选**——这三类删错/漏掉的代价最高，而自信最不可信。
