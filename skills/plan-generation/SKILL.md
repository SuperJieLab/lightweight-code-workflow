# 落地方案 —— 从承诺到可执行的结构

> 这一节点只回答「用什么结构实现」，**不重述承诺**。spec 说过的不再说，只引用编号。
> 方案的内容可被执行阶段修正，这是它与 spec 的根本差别：spec 改一条就是范围变更，plan 改一节是正常推进。
> 推导步骤全部在六节的「可用手段」里，六节之外没有另一套——某一节答不上，就补那一节。

## 输入与依赖

**前置状态**：spec 的 `status` 为 `approved`，且本分期还没有 plan 或 plan 为 `draft`。**spec 未定稿就开始写方案，是这一节点最常见的越界**——那时你还不知道「做到什么算做到」。

**开工先读**：

- `spec.md` **全文六节**，不只是承诺表。第三节的可行性结论决定了哪些方向不用再试，第六节的范围外决定了哪些不该碰。
- `dev/RULES.md` 的目录承诺表 —— 结构基线复核要拿旧承诺对照。
- `dev/research/` 里相关的调研报告。

## 本节点负责的状态

| 从 | 到 | 条件 |
|---|---|---|
| 不存在 | `draft` | 建出 `plans/plan-<分期号>-<主题>.md` 骨架（哪怕只有标题） |
| `draft` | `approved` | 六节齐、过定稿检查、涉及结构类决策时已拷问过、用户明确批准 |

**`approved → draft` 的退回不由本节点发起**：执行阶段发现方案要变、或承诺要变时触发，退回时各文档该变成什么，查 `workspace-status` 的「回退」一节。

## 产出

一份 `dev/features/F<N>-<主题>/plans/plan-<分期号>-<主题>.md`，六节：覆盖哪些承诺、结构基线复核、实现方式与取舍、落地拆解、实施顺序与任务、判据表；模板另带修正记录与执行结果两个附录。

**格式按 `assets/plan.md.template`**——节次、表格列、任务块写法、两个附录都在那里排好了。本文只讲每节要判断什么、怎么取得、依赖哪些输入、变更后波及何处，**不复述格式**。

## 几条纪律

**六节构成一条推进链。** 承诺覆盖 → 结构基线 → 方式取舍 → 落地拆解 → 任务与判据，上一节的判断未落定，下一节即建立在推测之上。回改允许：按该节的「变更影响」确定哪些节须重新确认，改动本身记入文末修正记录。

**按缺口推进，不按节次推进。** 每节先写下当前的判断，再回头补最不清晰的一节。逐节写到底的常见结果是：第三、四节写完才发现第二节的关系列错，须回改两节。

**一条链，不并列。** 每节的判断应当从前一节的结论推出。同一节内出现两个并列的「核心问题」，说明前面缺了环节，回头补而不是并列解决。

**不替对方取舍。** 方案里凡是「选 A 还是选 B」这类承重决定，列出各自的代价交由用户决定。替对方选定之后，他会误以为那是自己的决定，而执行阶段一次前提不成立就会推翻整条路径。

## 六节怎么写

以下六节即方案的实质。每节分四块：**目的**（这一节要讲清什么）、**依赖**（须先具备哪些输入）、**可用手段**（参考做法，按需取用——以目的为准，手段无助于达成目的时应当更换或跳过）、**变更影响**（本节改动后，本文档哪些部分须重新确认）。部分节在「可用手段」之后附补充判据，仍属该块。格式以 `assets/plan.md.template` 为准。

### 一、覆盖哪些承诺

**目的**：spec 的每条承诺在本方案中均有落点；本方案不予解决的部分写明边界。

**依赖**：spec 第二、四、六节。

**可用手段**：

1. 打开 spec 第二节，逐条抄录承诺编号，不重写内容——重写会造出第二份表述。
2. 每条之后写明「本方案第几节兑现它」。
3. 无落点者二选一：补方案，或写入本节末尾的「本方案不解决的边界」。
4. 检查本方案拟改动的既有结构是否落在 spec 第六节「范围外」；落入者先改 spec，不在此处开口子。

**变更影响**：第二节起全链——覆盖范围一变，其后各节均须重看。

### 二、结构基线复核

**目的**：对每个既有依赖给出判定，完成双向举证，并使改动范围可追溯。产物是一张清单，不是一段叙述：叙述无法被检查，一句「经复核现有结构仍适用」即可敷衍。

**依赖**：第一节（需求决定必须存在的关系）。

**可用手段**：

1. 只从需求列出「必须存在的关系」，不看现有代码。三类：哪些状态必须由同一处持有（分开会不一致）；哪些变化必须同步发生（否则中间态对外可见）；哪些部分必须可独立替换。
2. 以这组关系对账现状，每个既有依赖落三种判定之一：关系所要求（保留）、历史偶然（可动）、关系要求而当前无承载（缺位，须新建或改向）。
3. 双向举证。「不变」须指出新需求落在既有的哪个变化触发源之下、既有承诺为何仍然必要；「变」须指出哪条既有承诺失效，且变更须换来此后同类改动更省。
4. 只动涉事部分。改动面须能追溯到本次需求引入的那条关系，追溯不到者一律不动。

「更友好」的判据四条：依赖指向变化更慢的一侧；一个文件只有一个变化原因；跨边界信息量最小；能由编译期强制。不接受「感觉更清晰」。

结构变更落地时同步更新 `dev/RULES.md` 的目录承诺表；未更新视为变更未完成。

**变更影响**：三（关系判定不同则可选路径不同）；四（时序与类型职责）；五（任务）；六（判据落在哪个接缝）。

### 三、实现方式与取舍

**目的**：沿需求链路选定一条实现路径，说明取舍、代价与反悔条件，逐条确认对 spec 不可协商约束的合规，并给出切面判断。**本节只回答「选哪条、为什么、何时回头」**；选定的那条由哪些时序与类型构成，属第四节；能否实现、他人如何解决、有无平台或协议限制，属 spec 的可行性一节，此处不重复。

**依赖**：spec 第二节的场景（链路由此展开）、本节点第二节判定的关系、spec 第三节的可行性与约束。

**可用手段**：先链路，再约束，后机制。

1. **枚举链路。** 一个场景一条，不合并——合并即丢失差异。每条写清谁调用谁、状态存放于何处、失败时如何返回，标出每步所在的层。多条并排比较，差异点即设计要点。
2. **界定边界。** 列出改不了的给定条件：环境与平台、规模、既有系统、不能动的部分、硬性期限。每条落成一个必须正视的问题，标「必须现在解」或「可延后为优化」，后者写明后果（只是体验差，还是会不正确、不安全）。两档分开记，不必求全。判据：每条都能指到代码、物理现象或外部硬性要求，且是给定条件而非已选定的方案。
3. **生成候选并收敛。** 针对每个差异变量列 2 至 3 条候选，各写适用条件与代价；参照的取用优先级同 spec 第三节，我们与参照只差的那个变量才是设计对象。只允许一个分岔点，出现多个说明问题还没想清；写清排除各项的理由。候选须能指回某条边界，指不回去的删掉。
4. **推演异常与识别优化面。** 沿时序逐环节问「这一步会怎样失败」：边界值、失败与重试、并发与竞态、非法输入、规模拐点、向后兼容。再回到目标找可改进处：性能、体验、成本、可维护性。两类记同一本账，每条归一个去处——已被「必须现在解」的边界覆盖、逼机制进化、降级为可延后并登记；优化点另须指回某条边界、异常或 spec 的目标。判据：每个机制至少被三个异常拷问过，没有异常逼得出来的机制通常说明没认真推。
5. **确定取舍与代价。** 选定路径在每条链路上走一遍，走不通说明选错了，回头重选。每条决定写明代价，至少留一条明确的「不做」，并写明何种情况下应回头选被排除的路径。判据落到一条命令或一个可观察现象；验证要证明目标被解决，不是接口通了、字段有了。
6. **复核不可协商约束。** 对 spec 第三节列出的每条约束，写一句「本方案不违反，因为…」。漏一条，执行阶段即被悄然推翻。
7. **判断切面处理。** 新增或修改跨边界行为时，写明三行：需要哪些切面、用统一设施还是模块内自建、理由。不涉及也须显式写「本分期无跨边界行为变化」。

跨边界三类：进出系统的（网络请求、深链、推送）；用户可见的状态转换（页面出现、提交、失败）；长期运行的（后台任务、定时器、重连）。

「使用统一设施」是现状断言，须取证：查统一设施接口、既有埋点规范，以及已有模块是否自建过同类设施（第三项是防止重复实现的关键）。

判据：切面调用点应与边界数量同阶，不与方法数量同阶。

**变更影响**：四（时序与类型由选定路径决定；某条链路在结构上走不通时回改本节，不在结构里迁就）；五、六；二（若边界推翻了某条关系判定，须回改）。

### 四、落地拆解

**目的**：把第三节选定的路径落成可实施的结构——交互时序、关键类型与职责、依赖层次与目录归属；归属表逐行给出理由与判据。**本节不重新选路**：链路已在第三节穷举并走通，此处只展开被选中的那条；走不通就回第三节，不在结构里迁就。

**依赖**：第三节。

**可用手段**：

1. **交互时序。** 按第三节的链路逐条展开，一条链路一张时序。时序先于类划分：一旦出现循环调用，说明两个类型应当合并，或缺一层。先划完类再画时序，返工的是类。
2. **关键类型与职责。** 每层答一遍「这一层归谁、复用什么、要新写什么」，得到新写清单。
3. **依赖层次与目录归属。** 纵向（链路）是骨架，横向（契约、复用、文件清单）只在本节汇总一次，两者叠加而非二选一。粒度按层：一层展开超过一屏说明混了两层；参数、接口名、超时值留到写代码那一刻现查，不预先囤积。

归属表（列见模板）三条硬要求：

- **粒度是符号，不是文件。** 混装是一次加一个符号长出来的：一个 480 行的文件可能从没有过一次「新增文件」的动作，按文件检查会全部通过。
- **第三列写判据，不写理由。** 「它是纯函数」「它属于协议」都不是判据；能当判据的只有：改它时另一处必须跟着改吗、它的消费者在哪一端、换了实现它要不要重写。
- **第四列答不出，说明这一刻没有判据。** 只有两条路：当场立一条（回填判据表），或明确记成「这是新的默认」并写清代价。留空不行。

**变更影响**：五（任务重排）；六（判据须对准新的接缝）。

### 五、实施顺序与任务

**目的**：按垂直切片排出任务，每个任务自带可执行判据与接口说明；删除动作独立成项。

**依赖**：第四节。

**可用手段**：

1. 将第四节的新写清单切成**垂直切片**——一个切片对应一个可观察行为。
2. 一个切片一个任务，配判据与接口签名。
3. 删除项独立成任务，不与改造任务混排。它即删除声明，精简阶段按任务清单对账，故不另设清单表。
4. 检查是否有任务跨越多个切片；跨越说明尚未切开，先切再排。

任务块的写法见模板。一条纪律：**一步一件事**（写失败用例 → 确认其失败 → 最小实现 → 确认通过）。「实现这个功能」不构成一步。

**变更影响**：六（任务增删须同步判据）。

### 六、判据表

**目的**：为每条承诺与每个任务给出判据并标明寿命；常驻判据须指到具体的测试断言。

**依赖**：一（每条承诺至少一条判据）；四（判据落在哪个接缝）。

**可用手段**：

1. 由第一节出发：每条承诺至少一条判据。
2. 由第五节出发：每个任务至少一条判据。

判据写法（列见模板）：

- 判据写 `输入 → 可观察输出`。「先收 seq=120 再收 seq=90，显示仍是前者」✓；「测试吸收逻辑」✗。
- 证明什么写这条判据排除了哪种错误，不重复判据本身。
- 寿命只有两个值：**一次性**（证明本分期做对，随本分期失效）与**常驻**（证明以后不许错，须可重复执行、落进测试套件）。常驻不得写成「人工 grep 一次」——那样它与一次性无异，下一个人不会重跑。写不成断言的，标「人工判据 + 下一次谁在何时重跑」；两样都写不出的，降级为一次性并说明为何留不下。

**判据先于实施，不是复核的产物。** 写完实现再想如何验证，验不了时改动成本已付。

**变更影响**：无下游。但本节变更后须回头确认第一节——部分承诺可能因此失去唯一判据。

### 模板还带两个附录

修正记录与执行结果的列与格式见模板。两条纪律：**修正记录的最后一列（影响的判据编号）不可省**——改结构往往要连带改判据，不同步改，复核重跑时要么失败要么空跑；**执行结果只留结论与指针**，细节留在 `checks/`，否则两份会不一致。

## 定稿

**交付之前过一次一致性检查。** 这些检查本应在每次改动时进行，列于此处的理由是：容易遗忘，而定稿前必须完成一次。

1. spec 的每条承诺在第一节都有落点？指不到的，是补方案还是进「不解决的边界」？
2. 结构基线复核是清单不是叙述？每条既有依赖都有三判之一？「不变」和「变」两个方向都举了证？
3. 第三节的链路逐场景列出、标了层次，并排比较后指明了差异点？方式用一句话给出了？每条边界标了「现在解 / 可延后」并写明延后后果？候选写了排除理由？每个机制至少被三个异常拷问过？每条决定写了代价，且至少有一条明确的「不做」？
4. 归属表每行四列都不空？第三列是判据不是理由？
5. 每个任务自带可执行判据？删除动作独立成项？
6. 判据表每条承诺与每个任务都有判据？常驻项指到了具体断言？
7. 有没有 TBD、「后续补充」、「加上适当的错误处理」这类占位？
8. 越界：有没有重述 spec 的承诺原文？有没有出现需求层的判断（该不该做）？

改了结构而判据未同步，是最容易遗漏的一处：重跑时判据仍在，验证的已是旧结构。

对方评审使用同一套检查项，**只报会导致真实问题的项**（缺节、矛盾、判据不可执行、越界重述）；措辞偏好、「某节不如另一节详尽」不构成阻塞理由。

### 门禁动作

本分期若涉及**结构类决策**（新建目录、新增跨层或跨端依赖、改动既有契约——判定见 `grill-me`），先走一遍，把沉默假设逼成显式取舍，回填进第三节的假设清单，再交 review。

交用户 review，**等明确回复**。通过后把 `status` 改成 `approved`，跑 `workspace-status` 拿下一步。

未获批准不得把状态改成 `approved`。执行阶段若发现要改 spec 的任何一条，停手把状态退回，不在方案里消化。

## 不做的事

- **不重述承诺**。引用编号即可。重述会产生两份表述，改一处漏一处。
- **不做需求判断**。「这功能值不值得做」「这是真问题还是症状」不属于这里，spec 已定。
- **不定编号、不改 spec**。
- **不预先写实现代码**。方案里出现的代码只允许一种：某个决策用代码比用散文更精确（状态机、reducer、schema、类型形状），内联并注明是原型。
- **不自行推进**。改完状态回 `workspace-status`，下一步由它给出。
