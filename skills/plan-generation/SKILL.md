# 落地方案

这一步在承诺已定之后、动手之前。它消除的风险是：承诺是对的，但实现路径选错了——结构上走不通、代价没人认、或者做到一半发现要拆的东西和想象的完全不一样。这类错误在代码写出来之前最便宜，写出来之后最贵。

产出是一份可以照着做的方案，读者是执行的人（可能是几周后的你）和复核的人。方案与 spec 的根本差别：spec 改一条就是范围变更，方案改一节是正常推进。

**方案写得浅，通常不是不认真，是每一步只答了「是什么」没答「为什么选它」。** 判据能证明没有明显缺失，证明不了它够用。决定深浅的是三件事：每个决定有没有写代价、每条被排除的路有没有写理由、判据能不能被反面实例推翻。

## 输入与依赖

进入前 spec 必须已 `approved`——未定稿就写方案，是这一步最常见的越界，那时你还不知道「做到什么算做到」。

**从 spec 拿四类信息，按类找，不按位置找**：

1. **承诺清单**——要兑现什么，带编号。
2. **硬约束**——不得违反什么。
3. **范围外**——不许在哪里开口子。
4. **可行性与已排除的路线**——哪些方向不用再试。

四类里缺任何一类，不要自己补，退回 spec 补。在方案里补承诺，等于把承诺层偷偷下移，最后核验时对照不到——这是最难查的一种越界，因为它看起来像顺手补全。

还要读：`dev/RULES.md` 的目录承诺表（结构基线复核要拿旧承诺对照）、`references/structure-rules.md`（归属判定的依据库）、`dev/research/` 里相关的调研报告、**spec 的缺口清单**——还没解的那几条在这里继续追，不另起一张。

## 流程

六步，每步的产物是下一步的输入。上一节没落定，下一节就是建在推测上。允许按缺口推进：哪一步最不清楚先补哪一步，但补完要回头确认前面没被推翻。

### 一、覆盖承诺

把承诺编号逐条抄下来，不重写内容——重写会造出第二份表述，改一处漏一处。每条后面写明本方案在哪一节兑现它。

无落点的二选一：补方案，或写进本节末尾「本方案不解决的边界」。后者要用户认可。

顺带检查：本方案拟改动的既有结构，有没有落在 spec 的范围外。落在里面的，先改 spec，不在这里开口子。

### 二、结构基线复核

产物是一张清单，不是一段叙述——叙述没法被检查，一句「经复核现有结构仍适用」就能敷衍过去。

**只从需求列「必须存在的关系」，不看现有代码。** 三类：哪些状态必须由同一处持有（分开会不一致）；哪些变化必须同步发生（否则中间态对外可见）；哪些部分必须能独立替换。

**拿这组关系对账现状。** 每个既有依赖落三判之一：关系要求的（保留）、历史偶然的（可动）、关系要求而当前无承载的（缺位，须新建或改向）。

**双向举证。** 「不变」要说清新需求落在既有的哪个变化触发源之下、既有承诺为何仍必要；「变」要指出哪条既有承诺失效，且变更能换来此后同类改动更省。只举一个方向，等于没判。

**判既有归属。** 本次触及的每个既有文件，先反查它属于哪个功能，再数该功能散在几个目录、跨目录引用几条（`python3 <本 skill 目录>/scripts/structure-probe.py <仓库根> --feature <关键词>`；指标定义与语言适用性见 `references/structure-rules.md`）。三判：合理（一个功能一个目录，或虽分散但每处各有判据）、应搬（散在 3 个以上目录，或单目录文件数超 20 且主题各异，须写出当前数字与搬迁后的预期数字）、不动（分散，但本次触及的部分不足以收拢）。

**给不出数字的一律判「合理」。** 没有数字的「感觉这块该整理」不是判据，它会让每次方案都背上说不清的整理工作。范围只限本次触及的功能，不做全库扫描。功能词从改动文件的路径段与文件名里取业务名词，去掉 controller / service / model / view / util / helper / common 这类层级词；取不出业务名词、只剩层级词的，这个文件本身就是混轴的产物，即「应搬」的证据。

**只动涉事部分。** 改动面追不到那两类来源的一律不动。

「更友好」的判据四条：依赖指向变化更慢的一侧；一个文件只有一个变化原因；跨边界信息量最小；能由编译期强制。不接受「感觉更清晰」。目录该沿哪条轴切、混轴有哪些症状，用 `references/structure-rules.md`，与本处四条各答一件事。

判为「应搬」的进「落地拆解」，成为独立任务项，搬迁与内容修改分开提交；结构变更落地时同步更新 `dev/RULES.md` 的目录承诺表，未更新视为变更未完成。

### 三、实现方式与取舍

这一节只回答「选哪条、为什么、何时回头」。选定的那条由哪些时序与类型构成，属「落地拆解」；能不能做、别人怎么解、有无硬限制，属 spec，不重复。

**先链路，再约束，后机制。**

**枚举链路。** 一个场景一条，不合并——合并即丢失差异。每条写清谁调用谁、状态存在哪里、失败时怎么返回，标出每步所在的层。多条并排比较，差异点就是设计要点。

**界定边界。** 改不了的给定条件：环境与平台、规模、既有系统、不能动的部分、硬性期限。每条落成一个必须正视的问题，标「必须现在解」或「可延后」。可延后的写明后果——只是体验差，还是会不正确、不安全。这一档判错，后面全歪。判据：每条能指到代码、物理现象或外部硬性要求，且是给定条件而非已选定的方案。

**生成候选并收敛。** 针对每个差异变量列 2 至 3 条，各写适用条件与代价。参照的取用优先级同 spec 的可行性与边界——我们与参照只差的那个变量，才是设计对象。只允许一个分岔点，出现多个说明问题还没想清。排除的每条写清理由。候选指不回某条边界的，删掉。

**推演异常，识别优化面。** 沿时序逐环节问「这一步会怎样失败」：边界值、失败与重试、并发与竞态、非法输入、规模拐点、向后兼容。再回到目标找可改进处：性能、体验、成本、可维护性。两类记同一本账，每条归一个去处——被「必须现在解」的边界覆盖、逼机制进化、降级为可延后并登记。判据：每个机制至少被三个异常拷问过；没有异常逼得出来的机制，通常说明没认真推。

**定取舍与代价。** 选定路径在每条链路上走一遍，走不通说明选错了，回头重选。每条决定写代价，至少一条明确的「不做」，并写明何时该回头。判据落到一条命令或一个可观察现象；验证要证明目标被解决，不是接口通了、字段有了。

**复核硬约束。** 对 spec 里标为硬的每一条，写一句「本方案不违反，因为…」。漏一条，执行阶段就会被悄然推翻。

**判断切面处理。** 跨边界三类：进出系统的（网络请求、深链、推送）、用户可见的状态转换（页面出现、提交、失败）、长期运行的（后台任务、定时器、重连）。沾到任一类写三行：需要哪些切面、用统一设施还是模块内自建、理由。不涉及也显式写「本分期无跨边界行为变化」。「用统一设施」是现状断言，要取证：查统一设施接口、既有埋点规范、以及已有模块是否自建过同类设施——第三项是防重复实现的关键。切面调用点与边界数量同阶，不与方法数量同阶。

### 四、落地拆解

把选定的路径落成结构：交互时序、关键类型与职责、依赖层次与目录归属。**不重新选路**——链路已在「实现方式与取舍」里走通，这里只展开被选中的那条；走不通就回去重选，不在结构里迁就。

**交互时序。** 按「实现方式与取舍」里的链路逐条展开，一条一张。时序先于类划分：出现循环调用，说明两个类型该合并，或缺一层。顺序反了，返工的是类。

**关键类型与职责。** 每层答一遍「这一层归谁、复用什么、要新写什么」，得到新写清单。

**依赖层次与目录归属。** 纵向（链路）是骨架，横向（契约、复用、文件清单）在本节汇总一次，两者叠加不二选一。粒度按层：一层超过一屏说明混了两层；参数、接口名、超时值留到写代码时现查，不预先囤积。

归属表三条硬要求：**粒度是符号不是文件**——混装是一次加一个符号长出来的，480 行的文件可能从没有过一次「新增文件」的动作，按文件检查会全过。**第三列写判据不写理由**——「它是纯函数」不是判据，能当判据的只有：改它时另一处必须跟着改吗、它的消费者在哪一端、换了实现它要不要重写。**第四列答不出，说明这一刻没有判据**——要么当场立一条并回填判据表，要么明确记成「这是新的默认」并写清代价，留空不行。

### 五、实施顺序与任务

按垂直切片排：一个切片对应一个可观察行为，一个切片一个任务，配判据与接口签名。

删除项独立成任务，不与改造任务混排。它本身就是删除声明，精简阶段按任务清单对账，不另设清单表。

检查有没有任务跨了多个切片——跨了说明还没切开，先切再排。

**任务清单定了就不再改号。** 执行中发现在某个任务里多做了事，把它作为**追加任务**接在那个任务后面，写成 `T4+1`、`T4+2`——加号表示追加。旧编号一个不动，判据表按 `T4+1` 引用。加号与点号分工：`+` 是追加的新任务，`.` 留给「一个任务拆成几个子步骤」，两者别混用。

任务块写法见模板。一条纪律：**一步一件事**（写失败用例 → 确认失败 → 最小实现 → 确认通过）。

### 六、判据表

每条承诺至少一条判据（从「覆盖哪些承诺」出发），每个任务至少一条（从「实施顺序与任务」出发）。

判据写 `输入 → 可观察输出`。「先收 seq=120 再收 seq=90，显示仍是前者」是判据；「测试吸收逻辑」不是。「证明什么」一栏写这条判据排除了哪种错误，不重复判据本身。

寿命只有两个值：**一次性**（证明本分期做对，随本分期失效）与**常驻**（证明以后不许错，须可重复执行、落进测试套件）。常驻不许写成「人工 grep 一次」，那与一次性无异，下一个人不会重跑。写不成断言的，标「人工判据 + 下一次谁在何时重跑」；两样都写不出，降级为一次性并说明为什么留不下。

判据先于实施。写完实现再想怎么验，验不了时成本已经付了。

模板另带三个附录：修正记录、执行结果、缺口。修正记录的最后一列（影响的判据编号）不可省——改结构往往要连带改判据，不同步改，复核重跑时要么失败要么空跑。执行结果只留结论与指针，细节留 `checks/`。**执行结果在 `closed` 时定稿**：复核与精简都可能让代码再变一次，`done` 时写的总结会变成过期快照，而 `spec-verify` 读的正是它。

## 每一步必须有什么

六步各有它必须回答的问题。答不出时不要靠改措辞过关，按最后一列处置。

| 步 | 必须回答 | 缺了怎么办 |
|---|---|---|
| 覆盖承诺 | 每条承诺落在哪一节；有没有改动落在 spec 范围外 | 无落点的，补方案或写进「本方案不解决的边界」交用户认可，不自己判 |
| 结构基线复核 | 三条必须存在的关系；每个既有依赖的三判之一；双向举证 | 举不出「不变」的理由，说明这一处该动；举不出「变」的收益，说明不该动 |
| 实现方式与取舍 | 选定哪条；代价是什么；何时回头；至少一条明确的「不做」 | 写不出代价，说明还没比较；没有回头条件，选错了只能硬走 |
| 落地拆解 | 时序、类型职责、依赖层次与目录归属 | 出现循环调用说明类型该合并或缺一层，回上一步 |
| 实施顺序与任务 | 一个切片一个任务，任务不跨切片，每任务自带判据 | 任务跨切片，说明还没切开 |
| 判据表 | 每条承诺、每个任务都有判据；判据可被反面推翻；常驻可重跑 | 写不成断言的降级为一次性，并写明为什么留不下 |

## 缺口清单

spec 的缺口清单没解完的，接着解；本步新发现的，往下加。格式与 spec 一致：状态四选一（未查 / 查到 / 查不到 / 待用户定），绑「影响哪条承诺或哪个任务」，终止条件是清单为空。

在方案阶段新冒出来的缺口，多半是「结构上走不通」而不是「信息不够」——那类问题不要记成缺口，它属于流程第三步的链路走不通，回头重选路径。

## 边界取舍

**这条判断会不会改变「做到什么算做到」。** 会，回 spec 改，走退档；不会，只影响怎么实现，留在这里。

灰区问一句：这个选择变了，用户会不会说「这不是我要的」。会，是承诺；只会说「实现方式换了」，不是。

方案里凡属承重决定的（选 A 还是选 B），列代价交用户定，不替他选——替选之后他会误以为那是自己的决定，而执行阶段一次前提不成立就会推翻整条路径。

## 参考样式

`assets/plan.md.template` 按六步排，另带三个附录（用法已在流程里各说一处，不重复）。节可以按分期大小调整；六步的先后不能丢——每步的产物是下一步的输入。

## 状态与交接

| 从 | 到 | 条件 |
|---|---|---|
| 不存在 | `draft` | 建出 `plans/plan-<分期号>-<主题>.md` |
| `draft` | `approved` | 退出判据全部成立、结构类决策已拷问过、用户明确批准 |

分期不在这里定义：spec 批准时已按改造步骤的依赖分组定死 `phases`，一组一期。本节点只写其中一期，写完一期、做完再写下一期——第二期的方案要依赖第一期落地后的代码形态，提前写依据只能是想象。

涉及结构类决策（新建目录、新增跨层或跨端依赖、改动既有契约）时，先走一遍 `grill-me`，把沉默假设逼成显式取舍，回填进「实现方式与取舍」的假设清单，再交评审。

批准是用户的动作，不要自己写「已批准」。执行阶段发现要改 spec 的任何一条，停手退回，不在方案里消化。

## 退出判据

四条全部成立才算定稿：

**缺口清单为空。** 每条已落到「查到」「用户已答」或「查不到且写清代价与在哪一步定」。

**六步都答出了它该回答的问题。** 逐项对照「每一步必须有什么」，答不出的那一处要么补，要么明确降级并写清代价。

**删节测试通过。** 逐节问「删掉这一节，执行的人会不会做错」。答「不会」的，合并或删掉后重测。

**读者测试没有新问题。** 派一个全新上下文的子代理，交给它一句标准——「一个没参与这次讨论、但有本领域经验的人，能否只凭这份方案开始写代码，不必回头问作者」——收回的问题分三堆（方案已回答、次要、只有用户能答），只允许一轮。

然后说出全文最弱的一处，以及它为什么弱。改了结构而判据未同步，是最容易漏的一处：重跑时判据还在，验的已是旧结构。

## 不做的事

想法与对策成对写，左边是会上来的那句话，右边是替代动作。

| 念头 | 现实 | 替代动作 |
|---|---|---|
| 「spec 这块没写清，我先按理解补上」 | 补在方案里等于把承诺层下移，核验时对照不到 | 退回 spec 补，不在这里开口子 |
| 「A 和 B 都行，先写着，到时候再选」 | 没有选定就没有代价，执行时一次前提不成立就推翻整条路径 | 列代价交用户选，选定后再往下写 |
| 「这条路径应该能走通」 | 「应该」不是判据 | 在每条链路上走一遍，走不通就重选 |
| 「这块该整理一下」 | 没有数字的整理会让每次方案都背上说不清的活 | 给三个数字，给不出就判「合理」 |
| 「用户说先这样，够用了」 | 批准覆盖的是他看到的东西，他看到的是草稿 | 先跑读者测试，再问批准 |

三条单独列：

- **不自己取分期号。** 分期在 spec 批准时定死，本节点只写其中一期。
- **不加期。** 执行中发现还得多一期，不新建 `plan-N+1`——改 spec 的 `phases` 走退档，不在执行中偷偷加。
- **不重写承诺内容。** 抄编号，不抄表述；重写会造出第二份表述，改一处漏一处。
