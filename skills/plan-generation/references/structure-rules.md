# 结构判据库

> 用来判两件事：这个文件该住在哪，这个目录该不该存在。
> plan 第二节判归属时读它。结论不唯一时以本文件为准，不以体感为准。

## 一、先分清两类问题

| 问题形态 | 判据 | 处置 |
|---|---|---|
| 文件住错了地方 | 能一句话说出这个功能由哪几个文件组成，而这些文件在不同目录 | 搬文件，不动依赖方向 |
| 依赖方向错了 | 两个模块互相 `import`；两个功能共写一份可变状态；同一实体存在两套不一致的模型 | 动架构，搬文件救不了 |

一句话：**问题在「谁依赖谁」则动架构，在「文件住在哪」则搬目录。** 前者的失败在上线后才显现，后者的失败在 `import` 处当场显现——所以能搬的先搬。

## 二、切分依据四条，按此顺序取第一条成立的

一个目录只能沿一个轴切分。两条轴同时用，就是这个目录变乱的起点。

1. **变化原因。** 因同一件事而改的文件放一起。判据：改 A 时 B 是否必须跟着改。
2. **消费者。** 同一批调用方共用的放一起。判据：它的消费方集中在一边，还是散在互不相干的几边。
3. **生命周期。** 一起发布、一起替换的放一起。判据：换掉一个是否必然换掉另一个。
4. **技术层次**（入口 / 逻辑 / 数据 / 工具）。只在上面三条都不成立时用。

第 4 条不是错的，但它的适用面窄：它与前三条正交，一旦项目长到多个功能，「同一功能按层切成四份」就是必然结果。判据是数出来的，不是感觉出来的——见第四节。层次切成 `features/<功能>/` 内部的进一步细分仍然成立，因为那时轴只有一个。

依赖应指向更稳定的一侧，这条与 plan 第二节的「更友好四条」是同一条，不在此重复。

## 三、混轴症状三条

三条都是数得出来的，不需要读代码：

1. 同一功能的文件散在 3 个以上目录。
2. 某目录文件数超过 20，且文件主题互不相干。
3. 目录名只说得出一层（`services`、`helpers`、`utils`、`common`），说不出一块业务。

**深度大不是症状。** `features/order/service.py` 比 `services/order_service.py` 深一层，但功能从 3 个目录收到 1 个。深度是位置，分散是路数，路数少才是真的少走路。

## 四、两个主指标，两个诊断指标

| 指标 | 怎么算 | 读法 |
|---|---|---|
| **功能分布目录数** | 文件名或路径含功能关键词的文件，落在几个不同目录 | 主指标。1 最好，≥3 该切 |
| **跨目录引用条数** | 一个文件引用了自己所在目录之外的模块，计一条 | 主指标。搬迁前后各测一次，看它降没降 |
| 最大目录深度 | 最深的源码文件在第几层 | 诊断用。只配合第一项看，单看会误判 |
| 单目录文件数极值 | 某个目录里的文件数 | 诊断用。超过 20 且主题各异即杂物间 |

两个主指标都由 `scripts/structure-probe.py` 输出。不要口算，也不要估——估出来的数字不能用于「应搬」判定。

## 五、指标的语言适用性

| 语言 | 路径类指标 | 引用类指标 |
|---|---|---|
| Python、JS、TS、Dart | 可算 | 可算：文件级 `import` 能解析到目标文件 |
| Swift、Objective-C | 可算 | **不适用**：`import` 是模块级，模块内文件互引不写 `import` |
| Go、Java、Kotlin | 可算 | 部分：导入粒度是包，不是文件 |

不适用时只用路径指标，并在判定里写明「引用指标不适用，因为…」。不要用一条算不出数的指标去凑判据，那会让整节判定变成形式。

## 六、搬迁纪律

1. **一次搬一个功能，不搬半个。** 半个搬完，功能比原来更分散。
2. 用 `git mv`，保留文件历史，出事时 `git log --follow` 能追。
3. **搬迁与内容修改分开提交。** 混在一起，review 看不出哪里改了行为，回滚也拆不开。
4. 搬完立刻跑现有测试与构建。漏改的引用当场报错，这是搬迁唯一也是最大的优势。
5. 搬完同步 `RULES.md` 的目录承诺表，漏更新视为搬迁未完成。
6. 不同时改层级与目录名。
