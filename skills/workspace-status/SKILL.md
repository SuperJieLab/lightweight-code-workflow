# 工作区状态 —— 读状态、报矛盾、给下一步

> 它只读状态、只输出「下一步该跑哪个节点」，不调用任何 skill。
> 节点做完自己推进状态，然后回来问这里。流程知识只存在这一处，节点不需要知道后继是谁。

## 输入与依赖

**前置状态**：无。任何时刻都可跑，包括工作区还没建的时候——那种情况下第一步会说明转 `workspace-init`。

**输入**：仓库根目录。`dev/` 可能尚不存在，此时按「流程」第一步处理。

## 流程

第一步，检查 `dev/` 是否存在。不存在 → 输出「工作区未初始化，请先跑 `workspace-init`」，结束。

第二步，跑推导脚本：

```bash
python3 <本 skill 目录>/scripts/status.py <仓库根目录>
```

脚本输出三段（见「输出格式」），有矛盾时退出码为 1。脚本跑不起来时按「状态定义」与「转移表」人工推导，规则一致。不要因为脚本不可用就跳过矛盾检查，矛盾恰好在那时最容易积累。

第三步，**补脚本给不出的两段**（这一段是判断，不是推导）：

- **卡点与未决**：活跃 plan 里没勾完的任务、修正记录里没有闭环的项、`checks/` 最近一份报告里标了风险但没处理的地方、`ISSUES.md` 里与本阶段相关的条目。没有就明说「无」。
- **引用体检**：扫一遍活跃文档里的引用——节号引用（`§`、`第几节`）、旧目录名与旧文件名、枚举清单——逐条看是否还落得到实处。落不到的列进「卡点与未决」。**只列不改**，改法属于文档作者的事。

## 状态定义

只存在于两个地方，别处不许存：

```yaml
# dev/features/F<N>-<主题>/spec.md
---
feature: F12
topic: 未读按会话维度
status: draft        # draft | approved | delivered | superseded
phases: 3            # 本 spec 共几期；不写 = 1
---
```

```yaml
# dev/features/F<N>-<主题>/plans/plan-<分期号>-<主题>.md
---
feature: F12
phase: 1
status: draft        # draft | approved | executing | done | reviewed | closed | abandoned
---
```

**分期不是独立实体**：分期的状态就是那份 plan 的状态，分期号只是 plan 的属性。

## 转移表

这是整套流程唯一一处写「下一步是谁」的地方。

| spec | plans | 阶段 | 下一步 |
|---|---|---|---|
| `draft` | 任意，且全部为 `draft` | 承诺未定 | R1 `spec-generation` |
| `approved` | 第 k 期（k ≤ `phases`）的 plan 不存在 | 待写方案 | R2 `plan-generation` |
| `approved` | 有 `draft` | 方案未定 | R2 `plan-generation` |
| `approved` | 有 `approved` 未开工 | 待执行 | R3 `tdd` |
| `approved` | 有 `executing` | 执行中 | R3 `tdd` |
| `approved` | 有 `done` | 待复核 | R4 `code-review` |
| `approved` | 有 `reviewed` | 待精简 | R5 `code-slim-audit` |
| `approved` | 1..`phases` 每期都已 `closed` 或 `abandoned` | 待交付 | R6 `spec-verify` |
| `delivered` | 全部 `closed` | 已完成 | — |
| 任意 | 有 `abandoned` 且其余全 `closed` | 该分期已放弃 | 同上，按剩余 plan 判断 |

**「全部 closed」不是「现有 plan 都 closed」，是「声明的每一期都 close 了」。** 这份 spec 分几期由它头部的 `phases` 定，不由 plan 目录里现有几个文件定——只看现有文件，一期交付完就会被判成整个 spec 完成。`abandoned` 算已了结。

同一 Feature 有多个分期时，**取分期号最小的未完成分期**。取最后一个会错在这样的情形：F6 正在执行、F7 刚建 spec 尚未开工，取最后一个会定位到 F7。

## 合法的跃迁

只有下面这些，其余一律算矛盾：

- `spec`: `draft → approved`（需人批准）、`approved → delivered`（R6 完成）、`approved → draft`（承诺变更重开，同时该 Feature 全部 plan 退回 `draft`）
- `plan`: `draft → approved`（需人批准）、`approved → executing`（R3 开始）、`executing → done`（任务全勾且每项有结果行）、`done → reviewed`（R4 通过）、`reviewed → closed`（R5 完成）、任意状态 `→ abandoned`（需写理由）

典型非法跃迁，也是矛盾检查的重点：`executing → closed`（跳过复核与精简）、`draft → executing`（跳过批准）、`done → closed`（跳过复核）。

## 回退：退回时状态该变成什么

节点报告「需要退回」时，跨文档的状态重置在这里定义——这是编排知识，只在本文档维护。**本 skill 不改文件**，只给出应有的状态；由人或当前节点改写，改完再跑一次本 skill 确认无矛盾。

| 退回的原因 | 状态应该变成 |
|---|---|
| 承诺要变（spec 任何一条） | spec → `draft`；该 Feature **全部** plan → `draft`。理由是 plan 用编号引用承诺，承诺改了引用就断，留着 `approved` 的 plan 会让它引用一组不存在的前提 |
| 方案要变（假设被推翻、结构不成立） | 该 plan → `draft`；spec 不动。已实现的部分按需回退代码 |
| 实现要变（局部） | 状态不动，就地改 |

退回由当事人主动发起，与矛盾不同：矛盾来自本流程之外对文件头的改动。退回之后重跑一次本 skill，不应出现「spec 是 draft 却有非 draft 的 plan」这条矛盾；若出现，说明退回只改了一半。

## 矛盾检查

至少这七条，发现即如实摆出，**不擅自选边**：

1. `spec` 仍是 `draft`，但存在非 `draft` 的 plan（除主动重开的情形外，说明有人跳过了批准）。
2. `spec` 已 `delivered`，但存在非 `closed` 的 plan。
3. 分期号断号或重号。
4. 某分期 `approved`，但它依赖的前一个分期还不是 `closed`。
5. plan 的 `feature` 字段与所在目录编号不一致。
6. 任务勾选数与有结果行的任务数不等（脚本粗查：`- [x]` 数量 vs 统计块里 `结果：` 的数量）。
7. plan 的期号超过 spec 声明的 `phases`（多加了一期），或 `phases` 不是正整数。

矛盾不由状态机产生，它来自本流程之外对文件头的改动。报出之后由人决定怎么修，此处不做修复。

## 输出格式

```
## 状态

| Feature | 主题 | 阶段 | 下一步 | 阻塞 |
|---|---|---|---|---|
| F12 | 未读按会话维度 | 执行中 | R3 tdd | — |
| F13 | 群公告已读 | 待写方案 | R2 plan-generation | 依赖 F12 第 2 分期 |
| F11 | 会话置顶 | 待写方案 | R2 plan-generation | 第 2 期还没有方案 |

## 矛盾

- F13 的 spec 仍为 draft，但 plan-1 已是 approved；批准记录找不到。

## 卡点与未决

- F12 第 1 分期：T4 未勾选，判据等装配层落地
- F12 第 1 分期修正记录：第 3 条改了归属表，但判据 4 未同步更新
- `dev/ISSUES.md` #23 影响下一次结构变更，本阶段不处理

## 下一步

建议 `R3 tdd`（F12 第 1 分期）。理由：编号最小的未完成期，依赖已满足。
起点：plan-1 的 T4「会话列表接新数据源」，判据见该 plan 判据表中 T4 那条。

下一个可用编号：F14
```

**建议必须细到可以直接开工，并带出处指针。**「继续做 F12」不算建议；「plan-1 的 T4，判据见判据表中 T4 那条」才算。指针写 ID 或标题原文，不写节号位置——节号会随增删漂移。

**没有需要推进的 Feature 时，必须显式写**：

```
## 状态

当前无需动作。

可选的遗留：`dev/ISSUES.md` 里还有 3 条未结，其中 #23 标了「影响下一次结构变更」。

下一个可用编号：F14
```

沉默会被读成「漏了什么」，所以这一句不能省。

## 退出判据

输出含四段：状态、矛盾、卡点与未决、下一步；末尾一行 `下一个可用编号：F<N>`。

编号是唯一分配口。建目录的人必须用这一行，不得自行取 max+1——并行需求会撞号，撞号之后没有一处能裁决。

本 skill 不改任何文件，因此没有状态要推进。

## 不做的事

想法与对策成对写，左边是会上来的那句话，右边是替代动作。

| 念头 | 现实 | 替代动作 |
|---|---|---|
| 「下一步很清楚，我顺便把那个节点跑了」 | 进哪个节点由用户决定，这里内嵌调度会让流程知识散到两处 | 只说该跑哪个，不调用它 |
| 「这个矛盾我顺手修一下」 | 修意味着它得知道谁对，而它没有这个信息 | 报出来，让知道的人改 |
| 「文件头没写 status，看内容应该是 approved」 | 推断出的状态不可信，而且掩盖了「漏写」这个真问题 | 报「缺失」，不猜 |
| 「checks 里写通过了，就算这期做完了」 | 做没做完由 plan 的状态承载，checks 只记做过什么 | 读状态，不读过程文档 |
