# 需求核验 —— 承诺兑现了没有

> 拿 spec 的承诺对照实现。**复核对照的是 plan，不是 spec**，所以「承诺是否兑现」只能在这里判，不要指望前面的步骤已经覆盖。
> 不做调度：不调用别的 skill、不重跑判据、不补做复核与精简。顺序由状态承载，前置条件不满足就回去。

## 输入与依赖

**前置状态**：spec 为 `approved`，且 spec 声明的 `phases` 每一期都已 `closed` 或 `abandoned`。

有 plan 还停在 `done` 或 `reviewed` → 顺序被跳过了，**不要在这里补做复核和精简**，回 `workspace-status` 看它报什么。

**开工先读**：

- `spec.md` 全文 ——「需求拆解」逐条是核验对象，「能不能做，以及哪些边界可以先信」用来判断缩水是否越线。
- 全部 plan 的判据表与修正记录 —— 缩水要有批准痕迹，痕迹在这些地方。
- `checks/` 下本 Feature 的全部快照 —— 复核与精简的结论是核验的依据。

## 流程

### 一、核验承诺兑现

拿 spec「需求拆解」里的承诺逐条过，每条落四态之一：

| spec 承诺 | 结论 | 依据 |
|---|---|---|
| S1（原文摘一句） | **兑现** | 指向实现处（文件:行号）与验证它的判据 |
| S2 | **缩水** | 缩在哪、为什么、有没有经过批准（看修正记录与退档历史） |
| S3 | **未做** | 为什么、写进遗留还是退回 R1 |
| S4 | **已实现但未验证** | 实现处指向哪、缺哪条判据、谁来补、什么时候补 |

第四态是必须有的一项，不能并进「兑现」：代码在、判据没有，等于没人知道它对不对。它也不能就此关闭——要么补上判据转成兑现，要么明确降为未做并写进遗留。

四条纪律：

- **「兑现」必须指到可验证的地方。** 指不出判据的，落第四态，不写成兑现。
- **「缩水」必须有批准痕迹。** 缩水而没有任何一次退档记录，说明承诺被执行阶段悄悄降级了——这是必须报出来的问题，不是可以接受的偏差。
- **「已实现但未验证」必须带补法。** 只写「缺判据」不给谁在何时补，等于把问题留给下一个人，而那个人不会有现在的上下文。
- **对不上的地方不许含糊。** 「基本做到了」「大体符合」不是结论。

**到这里出现的「未做」，是方案漏了，不是留给下一期。** 期数已全部关闭，没有「下一期」可留。写进遗留并说清当初为什么没排进任何一期，或退回 R1 重开——不在这里直接置 `delivered`。

### 二、写结项记录

产物 `checks/YYYY-MM-DD-closeout.md`，属于过程文档：写完即固定，不回填。

五块，缺一块不算完成：

**核验结论** —— 上面那张四态表。

**偏差** —— 计划与实际的偏离，每条带当时理由。与 plan 的「修正记录」呼应，只做汇总不重复。

**跨分期发现** —— 会影响以后所有期的结论：新的外部依赖风险、新的项目级定义、跨 Feature 的技术判断。

**留下的判据** —— plan 判据表里标「常驻」的每一条，逐条写落在哪个测试文件的哪条断言，或「人工判据 + 谁在何时重跑」。指不出的写明为什么留不下来。**这是唯一跨分期累积的东西**，也是下一期的输入。

**遗留** —— 指回后续 plan，或指向 `dev/ISSUES.md` 编号，含判据降级项。

### 三、回写项目级

按判据决定改哪些，**不要为了「保持同步」把所有文档动一遍**：

| 文档 | 什么时候改 | 判据 |
|---|---|---|
| `PROJECT.md` | 本分期改变了对外可见的能力或使用方式 | 这个变更能被项目外的观察者感知吗？能才改。改「功能组织」那节，**不加 Feature 条目** |
| `RULES.md` | 新确立了工程规则，或目录承诺变了 | 这条规则以后每次作业都适用吗？ |
| `ISSUES.md` | 有遗留需要跨分期记住 | 不属于任何后续 Feature，但现在不做迟早要处理 |

`PROJECT.md` 里不写：本分期做了什么、分期号、进度、Feature 列表。

### 四、关闭 Feature

把 `spec.md` 的 `status` 改成 `delivered`——唯一能让 Feature 变终态的动作。

**停：`delivered` 要用户表态，不由执行者自行宣布。** 它与 `approved` 同级，都是用户的动作；区别在于 `delivered` 没有回头路——跃迁表里没有从它出发的合法路径，置错只能手改文件头，而那正好会被矛盾检查报成「有人跳过了流程」。把四态表与结项记录摆出来，等对方说可以关闭，再改这一行。

改完跑 `workspace-status` 确认无矛盾。

## 退出判据

六条同时成立：

1. spec 的每条承诺都有四态之一，没有一条停在「基本符合」；
2. 「缩水」项都有批准痕迹，没有的已作为问题报出；
3. 「已实现但未验证」项都带了补法（谁、何时）；
4. 结项记录五块齐全，常驻判据逐条指到落点或写明留不下来的原因；
5. `PROJECT.md` / `RULES.md` / `ISSUES.md` 按判据处理过（不需要改的不动）；
6. `spec` 已置 `delivered`，且 `workspace-status` 无矛盾。

## 不做的事

想法与对策成对写，左边是会上来的那句话，右边是替代动作。

| 念头 | 现实 | 替代动作 |
|---|---|---|
| 「有 plan 没关，我顺手把它复核了」 | 顺序被跳过意味着前面的结论不可信，补做会得到假的完整性 | 回 `workspace-status` 看它报什么，不在这里补 |
| 「判据没跑过，但代码写了，算兑现吧」 | 代码在、判据没有，等于没人知道它对不对 | 落「已实现但未验证」，写明谁何时补 |
| 「这条基本符合」 | 「基本」不是结论，交付时没人能据此判断 | 四态之一，指到实现处或判据 |
| 「顺手把文档全都同步一遍」 | 为了同步而同步，会把没变的也改一遍 | 按三条判据决定改哪个，不需要改的不动 |
| 「写一段总结与展望」 | 结项记录是过程文档，不是述职材料 | 只写事实：做了什么、验到什么、留下什么 |

一条单独列：

- **不删 `checks/` 里的历史快照。** 删掉之后同一个坑会再踩一次，而那时没人知道踩过。
