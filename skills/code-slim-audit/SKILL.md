# 精简 —— 判「还有没有人用」

> 单位是整库。核心判据只有一条：**这段代码还有没有会执行的引用路径。**
> 需求变更后旧链路整体废弃是死代码的主要来源，而它恰恰是静态工具最容易漏的形态——链路内部还在互相引用，只断了入口。

## 范围：只做死代码

冗余有五种形态，这里只处理第一种：

| 形态 | 处理方 |
|---|---|
| 死代码（无人引用、链路断开、被替代未下线） | **本 skill** |
| 过度抽象（只有一个实现还留着协议/工厂） | 复核 |
| 重复逻辑（两处做同一件事） | 复核 |
| 过度防御（不可能成立的分支） | 复核 |
| 过时残留（注释、开关、兼容层） | 复核 |

「复核」指在复核环节作为简化机会报告，改不改由方案决定；本 skill 只处理死代码。

判据：**删除是否可能改坏运行时行为。** 可能改行为的（重复逻辑合并、抽象去掉）属于结构变更，要让方案说话，本 skill 不接；只删除、不改行为的才归这里。

后四类里有两种特殊：**过度防御**与**过时残留**的删除同样不改行为，但它们「是否仍会被需要」取决于未验证的前提（防御分支所防的条件、残留所兼容的旧版本）。判断依据不成立就会误删，因此只报告、不在这里删。

## 输入与依赖

**前置状态**：plan 的 `status` 为 `reviewed`。

**开工先读**：

- plan「实施顺序与任务」里的删除任务清单——它是本 skill 的对账基准。
- `dev/RULES.md` —— 命名的历史约定、哪些是预留扩展点（判「勿动」时要用）。

## 流程

### 一、删除前的判定

**每一条「零引用」都要重新搜一遍**，子代理或工具给的结论只是线索。搜索必须覆盖下面四类，漏一类就会误删：

- **每个符号单独搜**。批量 alternation 的结果过长时会被截断，截断处就是漏掉的调用方。
- **测试侧**：测试框架的 setup/teardown 钩子、mock/fake 子类、`@override`、测试专用访问器。只搜生产代码会漏掉「只有测试在用」——那不算无人使用。
- **字符串与配置键**：路由或页面注册表里的目标名、依赖注入容器按类型解析、服务注册点、组合根装配点、前后端消息契约。这类引用不是符号调用，grep 符号名搜不到。
- **动态与隐式**：反射、KVC / selector、序列化字段名、DDL 列名、JSON key、xib / storyboard 的 outlet 与 action。

**删除前的三档判定**，按搜证结果定：

| 档 | 判据 | 处置 |
|---|---|---|
| 安全 | 零引用已自证，且不在上述四类的覆盖范围内 | 直接删 |
| 需确认 | 零引用，但落在动态引用可能命中的形态里 | 列进报告请人拍板，不自行删 |
| 勿动 | 有测试或有意设计支撑（分层约定、预留扩展点、对外契约的一部分） | 不删，在报告里写明为什么 |

搜完仍判不准的，按「需确认」处理。**误删一个仍在用的符号，比留一段死代码贵得多。**

若本分期改动面跨多个域，可按依赖层或职责分域并行（每域一个只读子代理），但**范围仍是本分期改动面加上被替代掉的旧实现**，不做全库。

### 二、按任务清单对账

plan 任务清单里写成任务项的删除动作（如「T5：删除 `X.legacy()` 与其旧测试」），逐项核对，每项落三种状态之一：

- **已删**：删了什么（符号 + 测试），指向 commit。
- **改为遗留**：为什么不删（仍被谁引用），写进本报告的遗留段，同时登记 `dev/ISSUES.md` 并按需要标「影响面」。
- **判定错误**：原计划说它无用，实际还在被用 —— 这是方案层判断错了，**回写 plan 的修正记录**（改动的节：归属表；影响：对应判据）。

漏掉一项没核对，本 skill 没做完。

### 三、静态扫描（候选生成器）

跑一遍项目可用的死代码检测工具，作为**候选来源**，不当判据用。

```bash
# 示意：具体命令按项目而定
periphery scan --quiet --format csv
```

三条纪律：

- **它报的每条都要人判定**，工具不知道你的意图，只知道引用关系。
- **先实测一次误报率再决定要不要纳入常规**。Swift 项目里 KVC、selector、字符串通知名、xib/storyboard 的 outlet 与 action、`NSClassFromString` 一律看不见，会报成「未引用」。没有实测数据之前别把它当验收条件。
- **工具只查直接引用，不查传递性死代码**：一条链路从入口到末端都还互相引用着，只是入口没了，工具一个都不会报。这一类只能靠任务清单对账和人工读时序。

扫出来的新候选（清单外的），处理方式两种：判定属实就删并补记进报告，判定不删就写进遗留并说明理由。

### 四、受影响判据

**不跑全套判据。** 只跑被删符号的调用面所覆盖的那些测试。

- 删掉的代码**有**测试覆盖 → 跑对应测试，全绿即可。
- 删掉的代码**没有**测试覆盖 → 跑全套也挡不住误删，所以改为在报告里写明：删了什么、凭什么判定没人用（引用搜索的结果、入口断在哪）。

判据：**删无测试覆盖的代码时，判定依据必须留痕。** 否则半年后没人能复核这次删除是否正确。

## 产出

`checks/YYYY-MM-DD-slim.md`：

```
## 任务清单对账
| 任务 | 状态 | 说明 |
|---|---|---|
| T5 删 X.legacy() | 已删 | 3 个符号 + 2 个测试（a1b2c3d） |
| T7 删 OldMigrationHelper | 改为遗留 | 仍被 v1 灰度路径引用 → ISSUES #24 |

## 静态扫描
- 工具：periphery 2.x
- 候选 12 条 → 删 4、误报 7（动态引用）、保留 1（写理由）

## 受影响判据
- UnreadTests：38 项通过
- ListTests：12 项通过
```

并回填 plan 的「执行结果」一节，一行结论加指针。

## 退出判据

三条同时成立：

1. 任务清单里每个删除项都落了三态之一；
2. 静态扫描报出的候选已处理（删除或记入遗留并说明）；
3. 受影响判据已跑，删无覆盖代码的判定依据已留痕。

然后把 plan 的 `status` 改成 `closed`，跑 `workspace-status` 拿下一步。

## 不做的事

- **不跑全套判据**。对「找漏删」无效（判据验的是「该有的还在」，不验「不该有的没了」），对「防误删」也只是弱覆盖。
- **不凭感觉删**。每条删除都要有可删的依据：被替代、失去最后一个调用者、或历史遗留登记。
- **不顺手重构**。精简只做删除，改结构属于方案层。
- **不把静态工具当验收条件**。它产候选，不产结论。
- **不删清单外的条目却不记录**。删了就在报告里说明，否则「为什么少了一段代码」永远查不到。
