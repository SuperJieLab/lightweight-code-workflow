# 执行 —— 红绿循环，一步一件事

> 这一节点的唯一产出是代码与测试，加 plan 里的任务勾选与结果行。
> **判据先行**：每条常驻判据先以失败状态存在，再写实现让它通过。这是「方案不成立」暴露得最早的时机——测试写不出来或者写出来变不绿，说明问题在方案层，不在实现层。

## 输入与依赖

**前置状态**：plan 的 `status` 为 `approved`。开工第一件事：把 `status` 改成 `executing`。

**开工先读**：

- plan 全文，其中「实施顺序与任务」与「判据表」两节逐条读完——它们是这一节点的输入，不是参考。
- `dev/RULES.md` —— 测试框架、测试文件位置、验证命令以它为准。

## 流程

### 一、开工前：接缝与测试质量

**测试通过公开接口验证行为，不碰实现细节。** 判据：代码可以整体重写，测试不该变。好测试读起来像规格——「用户能用有效购物车结算」说明存在什么能力——并且它在重构后依然成立，因为不关心内部结构。

**接缝**是能观察行为而不伸入内部的公开边界。**只在预先约定的接缝上测试**——但**接缝在方案阶段就定了**（plan 的「落地拆解」划出类型边界、「判据表」指出验哪里），执行阶段直接遵循，不在写测试时临时和用户约定新接缝。plan 里指不出接缝的，回方案阶段补，不要在实现里自己划一个。

**三个反模式，出现即改：**

| 反模式 | 特征 | 改法 |
|---|---|---|
| 实现耦合 | mock 内部协作者、测私有方法、绕过接口直接查存储。重构但行为没变，测试就挂 | 移到接缝上，只 mock 外部依赖（网络、DB、时钟） |
| 同义反复 | `expect(add(a,b)).toBe(a+b)`——用和代码相同的方式重算期望值，永远不可能不一致 | 期望值来自独立事实源：已知正确的字面量、手算样例、规格 |
| 水平切片 | 先写完所有测试再写所有实现。批量测试验证的是「想象的行为」 | 垂直切片：一个测试 → 一个实现 → 重复 |

### 二、一个任务的循环

1. **读任务的判据**。判据不可执行（没有命令、没有期望输出、没有可勾选的现象）→ 停，退回方案阶段补，不要在实现里自己发明验收标准。
2. **写失败的用例**。跑一遍，确认它红。没确认红过的测试不算判据——它可能压根没被执行。
3. **最小实现**。只做到让判据变绿，不做顺手优化。
4. **确认绿**。跑判据指定的命令，看到期望输出。
5. **勾选并写结果**：`- [x]` 加上 `结果：` 一行（做了什么、验到了什么、指向 commit 或测试输出）。

**勾选是自我报告，结果行是可核对的。** 只有勾选没有结果的条目会被 `workspace-status` 报出来（勾选数与结果行数不等）。

**循环之外的纪律：**

- **红在绿前。** 先写失败测试，再只写刚好让它通过的代码。不预判未来测试，不加投机功能。
- **一次一个切片。** 每轮一个接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 它属于精简节点，不在红绿里顺手做。
- **一轮 = 一个 Task = 一个 commit。** 绿了就提交，message 指回 Task 编号。不把多个 Task 攒成一个 commit。
- **本 skill 只定红绿纪律**，测试框架、测试文件位置与验证命令以 `dev/RULES.md` 为准，不在这里另立一套。
- **切面在边界处一处一次。** plan 的「实现方式与取舍」写了切面处理，就按那里写的落点做，不要在每个内部方法里加日志；写完核对切面调用点数量应与边界数量同阶。

### 三、循环中的意外

**用户要求小改**：先看它改变什么。只改实现方式（三层分流第一层）→ 直接做，不记；动了 plan 的依赖方向、类型职责、目录归属或任务顺序（第二层）→ 一轮红绿做掉，在 plan 任务清单补一行 `[小改] 日期 一句话（做了什么 + 为什么）`，并按修正记录追加；触及 spec 任何一条（第三层）→ 停，走退档。

**同一条判据连续两次变不绿**，且失败原因指向「这个结构不成立」而不是「我写错了」→ **停手上报**，不要换第三种写法继续试。「感觉不对就上报」不可执行，因为感觉没有阈值；「连续两次」有。上报的内容三句：卡在哪条判据、两次分别试了什么、为什么判断这是结构问题。

**方案要变：三层分流**

| 改变了什么 | 处置 |
|---|---|
| 只是局部实现方式（方法签名、内部拆个辅助类） | **不记**，代码本身就是记录 |
| plan 的依赖方向、类型职责、目录归属、实施顺序 | **回写 plan 对应节**，并在「修正记录」追加一行 |
| 任务里发现原范围外的新活 | 先判一句：**它会改变某条承诺的兑现方式吗？** 不会 → 追加成 `T4+1`，回写任务清单 + 修正记录一行；会 → 按下一行处理 |
| spec 的任何一条（承诺、边界、范围外、改造步骤） | **停**，报告需要退回；退回时各文档的状态该变成什么，查 `workspace-status` 的「回退」一节，不在这里自行改写承诺 |

第三层必须阻断而不是提醒。它的失败方式很具体：做到一半发现某条承诺做不到了，写一句「实施阶段修正：该需求暂不支持」记进 plan 然后继续，承诺就这样被静默降级，没人批过。

修正记录五列：`日期 | 改动的节 | 原判断 | 新判断与依据 | 影响的判据编号`。最后一列别省——改了结构往往要连带改判据，不同步改，复核重跑时要么失败要么空跑。

**已实现的代码怎么办**：看改动是否波及已经绿了的部分。波及就回退重做，只涉及未实现部分就继续。

## 退出判据

两条同时成立：

1. plan 的任务清单全部勾选，且每项都有结果行；
2. 判据表里标「常驻」的每一条，都在测试套件里且当前为绿。

然后把 plan 的 `status` 改成 `done`，跑 `workspace-status` 拿下一步。

进度不满足时不要改状态——`done` 的定义就是「全部勾选且每项有结果」。

## 不做的事

- **不顺手重构**。看到不相关的问题记进 `dev/ISSUES.md`，不在这里改。改动面必须能追溯到本次需求引入的那条关系。
- **不跳过红**。没确认失败过的测试，通过了也不证明任何事。
- **不发明验收标准**。判据不可执行就回去补方案。
- **不改 spec**。任何 spec 层的发现都走退档，不在执行阶段悄悄消化。
- **不自行推进**。状态改完回 `workspace-status`。
