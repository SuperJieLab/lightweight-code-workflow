# 需求分析

这一步在需求提出之后、方案之前。它消除的风险是：需求到手时是多解的，而验收口径在动手前不可判定——等做到一半才发现两边理解不同，那时返工最贵。

它的产出是一份需求分析，读者是没参与这次对话的人：下一步写方案的人、几周后回来验收的人、几周后的你自己。文档只是把想清楚的东西说出来，想清楚本身才是这一步的活。

## 输入与依赖

**前置状态**：`dev/` 已存在。没有就转 `workspace-init`，不要在别处建一套平行目录——两套并存之后，状态不知道该信哪个。

**编号来自外部**：Feature 目录的 `F<N>` 由 `workspace-status` 分配，本 skill 不取 max+1。

**开工先读**：

- `dev/README.md` 与 `dev/PROJECT.md` —— 这个工作区怎么用、项目现在是什么样。
- `dev/RULES.md` —— 既有工程规则与目录承诺表，写边界时拿它当基准。
- `dev/research/` 下与本需求相关的报告 —— 已有的证据不必重查，缺的按 `research` 补。

## 规范

产出要满足五条，缺一条，文档就只是素材的堆砌——读者看到的是内容，不是判断。

**一、现状与目标都能指到具体位置。** 不是「优化体验」，是「哪个帧的哪个字段」。指不到位置的两端，验收时分不清新增与回归。

**二、要求能指回依据，依据能被核对。** 依据是调研报告的某节、代码某处、一次实测的输出。核不上的依据是装饰，删掉或补取证。

**三、能不能做有结论。** 能做、不能做、有条件能做，三选一。写「基本可行」等于没结论，下一步无法据此决定要不要开始。

**四、每条边界带反悔条件。** 硬约束写清为什么硬；暂定判断写清什么情况下可以推翻。没有反悔条件的边界，后面想改时会变成违约。

**五、完成有独立判据。** 只能说「东西都在」的判据，证明不了「没混进别的东西」。

以上五条约束「产出必须满足的性质」。另有一条**机械约束**，不列进上面五条：

**「需求拆解」每一条用有序列表写，第 1 条即 S1、第 2 条即 S2，编号一经分配不改、不重用。** plan 的「覆盖哪些承诺」表与 `spec-verify` 的三态表都按这个编号引用；改号之后那些引用会指向另一条承诺，而且不报错——已经做完的方案看上去像是在做别的事。

## 指导思路

### 拆解从名词开始

需求通常是一句「让 A 能 B 这个 C」。拆解是把 A、B、C 逐个落下去：A 是哪一层、哪个入口；B 的触发条件、结果落在哪、失败时什么表现；C 是上游哪个类型、我们收到没有、存在哪。

落不下的名词就是这次的歧义，回去问；落到两个地方说明范围要拆。这一步不追求拆得全，追求拆得落——一个词落到位置上，比十个词列成清单有用。

### 调研的三个方向

顺着名词找定义与调用；顺着数据走一遍，从来源到消费，每站都是可能的改动点与回归点；顺着影响面向上看谁依赖我、向下看我依赖谁。

三个方向按需取用，不必都走完。调研材料落 `dev/research/<主题>.md`，一份报告一组证据；文档只放结论与关键依据，其余留在报告里。

现状最容易被想当然：文件存在、注释这么写、有人提过，都推不出它正在被使用。这类错误的特点是要到事后才暴露，而那时已经改在上面了。

### 整理是四次取舍

素材是调研时一条条记的，文档是按读者的问题组织的，两者不是一回事。

**去重**：同一个事实只写一处，其余改为引用，否则迟早一处改了一处没改。**归并**：零散的观察归到同一个问题下。**判权重**：进不进文档看「不写它，读者会不会判断错」，会才写，其余留在调研报告里。**找矛盾**：两处素材互相打脸，必须先判掉一处，不能都写进去。

### 呈现按一条轴组织

全文只能有一个组织轴：按链路（新增了若干条可观察路径，一条一节）或按层（修正的是与既有结构的偏差，坐标系用对方的分层）。混用要指定主轴。混轴的症状是有些节按模块写、有些节按时序写，读者以为分了两层。

每一节要能被上一节推出来。推不出的内容是并列，不是推进，读者会问「这跟上面什么关系」——那就是硬塞。

## 边界取舍

**这条信息变了对端要不要跟着改。** 要，是承诺，留在这里；只有自己仓里换，留给下一步。

灰区问一句：这条变了，用户会不会说「这不是我要的」。会，是承诺；只会说「实现方式换了」，不是。

写的时候必然会做小取舍，比如选哪种粒度描述、先动哪一层。这不是越界，不必因此自我审查。真正要守的只有一条：**拿不准的不补全，标出来。** 补全之后，对方会以为那是自己的决定——这是这一步最难察觉的失败，因为它当时看起来像效率。

## 参考样式

`assets/spec.md.template` 按「诉求 → 背景与现状 → 能不能做以及边界 → 需求拆解 → 改造步骤 → 收口 → 范围外 → 假设」排。样式可以随需求变，对应关系不能丢：前两节回答现在与目标，中间两节回答能不能做与改哪里，后三节回答怎么算做到与不做什么。

## 状态与交接

| 从 | 到 | 条件 |
|---|---|---|
| 不存在 | `draft` | 建好 `dev/features/F<N>-<主题>/`，写出第一版 |
| `draft` | `approved` | 五条规范成立，用户明确说这份可以了 |

编号用 `workspace-status` 给出的那一行，不自己取 max+1：并行需求会撞号，撞号之后没有一处能裁决。

**批准时同时定死 `phases`。** 改造步骤按依赖分组，一组一期，组数就是期数，写进文件头。它是这套流程判「这份 spec 做完没有」的唯一依据——没有它，一期交付完就会被当成整个 spec 完成。定了之后要改就是范围变更，走退档，不在执行中偷偷加一期。

批准是用户的动作，不要自己写「已批准」。想法被认可不等于文档被认可，文档被认可不等于方案被认可。

改动已 `approved` 的承诺属于重开，不属于编辑：`status` 退回 `draft`，该 Feature 的 plan 同时退回。

交给下一步的是三样：每条要求的编号；每处改动牵动的面（用可命名的职责边界，不用类名与文件路径）；需要先定死的形状（改前与改后）。

## 交付前

把自己当作没参与调研的人读一遍。读完能不能从文档本身重建判断路径？不能，说明素材是堆上去的。然后说出全文最弱的一处，以及它为什么弱。

## 不做的事

- **不替对方补全。** 拿不准的标出来问，不写一个合理默认值然后当已定。
- **不自己写「已批准」。** 批准是用户的动作；想法被认可不等于文档被认可。
- **不自己取编号。** 用 `workspace-status` 给的那一行。
- **不在本节点消化承诺变更。** 已 `approved` 的承诺要改，是重开（退回 `draft` 并连带 plan 退回），不是编辑。
- **不把素材堆成文档。** 调研记的是素材，文档按读者的问题组织，中间隔着四次取舍。
