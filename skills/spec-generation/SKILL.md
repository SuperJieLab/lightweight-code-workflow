# 需求意图 —— 把想法变成可判定的承诺

> 本节点产出**一份双方都认得的承诺**，不是方案。只回答「做什么、做到什么算做到、不做什么」；出现具体文件路径、类名或依赖指向即为越界，属于方案层。
>
> **门禁**：写产品代码、搭脚手架、装依赖、建外部工程，一律排在 spec 定稿之后。只读的探索（读文件、看文档、查提交历史、跑只读命令）不受限制，不因「尚未定稿」而放弃取证。
>
> 关于「这点事走什么流程，直接改吧」：直接改代码不在本节点辖区，但一项改动是否属于「不构成 Feature 的改动」有明确判据——**不引入新承诺、不改 spec 任一条**；**不改依赖方向、类职责、目录归属**；**不需新判据**（现有测试能覆盖，或改动本身无行为变化）。三条同时满足才可直接做，任一条不满足即从本节点起走完整流程。

## 输入与依赖

**前置状态**：spec 不存在，或存在而 `status` 为 `draft`。两种进入方式——新建（`dev/features/` 下尚无对应目录）、重写（已有 spec 而状态退回 `draft`）。

**开工先读**：

- `dev/RULES.md` —— 命名、目录承诺、文档与引用纪律；本 skill 未覆盖之处以其为准。
- `dev/PROJECT.md` —— 现有能力及其边界，用以判断该需求是否已存在。
- 既有 `spec.md`（重写时）—— 逐节读完，判断本次变更落在哪几节。
- `dev/research/` —— 同一事实不必二次取证。

## 本节点负责的状态

| 从 | 到 | 条件 |
|---|---|---|
| 不存在 | `draft` | 建好 `dev/features/F<N>-<主题>/` 并写出骨架，至少含六节标题 |
| `draft` | `approved` | 六节均已写清、一致性检查通过、用户明确批准 |

`approved → draft` 的退回不由本节点发起：执行阶段发现承诺需要变更时触发，退回后各文档应处于何种状态，见 `workspace-status` 的「回退」一节。

## 产出

一份 `dev/features/F<N>-<主题>/spec.md`，六节：问题陈述与当前基线、场景与要求、可行性结论与不可协商约束、方案分期、收口判据、范围外。同时建空目录 `plans/`。

**格式以 `assets/spec.md.template` 为准**——节次、表格与占位提示均已排好。本文只说明每节要讲清什么、依赖什么、有哪些可用手段、变更后波及何处，不复述格式。

编号取自状态查询输出末尾的 `下一个可用编号：F<N>`，不得自行按 max+1 推导：并行需求会撞号，撞号之后没有一处能够裁决。

## 几条纪律

**文档先行。** 初步沟通结束后即落骨架，未知处标注「待定：…」。讨论应基于文档而非记忆：无文档时各方凭记忆推进，记忆会各自生长；有文档时异议可指向具体一节。每轮改写后说明本次改动落在哪几处。

**按缺口推进，不按节次推进。** 哪一节尚不足以写清，就先补哪一节。不清晰的一节往往决定其他几节的答法；按顺序逐节填写，常见结果是写到第三节才发现第一节的基础是推测。

**不替对方补全。** 未确定之处当面提问。补全之后，对方会误以为那是自己的决定——这是本节点最常见也最难察觉的失败。

**对方提出的疑问，先取证再答。** 不得凭印象作答；答案须落到文档对应节，仅停留在对话中的结论，接手者无从得知。

**需求过大时先拆。** 判据为「一个可独立实施的子系统」：一份 spec 装得下、每个分期都能独立交付、一个观察者能验收，三条同时满足才无需拆分。

需要逼出假设走 `grill-me`，需要外部事实走 `research`；需求点落入既有系统时，先做下面这一步。

### 影响评估

需求点要落入已存在的系统时，动笔前先判断它改变了什么：

- 落入既有 spec 的哪几节，是否触动**已 approved** 的承诺；
- 是否与某个 plan 已定的结构（依赖方向、类型职责、目录归属）冲突；
- 结论有三种：**纯新增**（不触动既有承诺，正常起草）；**扩展**（改动既有承诺而范围可控，逐条列出被改的承诺编号）；**冲突**（须推翻既有承诺，走退档）。

判据：**改动已 approved 的承诺属于退档，不属于编辑。** 在 draft 稿中改写一条已批准的承诺，等于使该项承诺从未被批准。

## 六节怎么写

以下六节即 spec 的实质。每节分四块：**目的**（这一节要讲清什么）、**依赖**（须先具备哪些输入）、**可用手段**（参考做法，按需取用——以目的为准，手段无助于达成目的时应当更换或跳过）、**变更影响**（本节改动后，本文档哪些部分须重新确认）。

### 一、问题陈述与当前基线

**目的**：陈述当前行为的实际基线——系统现在怎样运转，精确到可观察的层面；并说明该问题出现时会发生什么，以及为何这是问题而非症状。缺此节，验收无法区分「新增」与「回归」。

**依赖**：无前置节次；事实来自代码阅读或取证，不得引用记忆。

**可用手段**：

1. 沿链路入口走一遍现有路径：谁调用谁、状态存放于何处、失败时会发生什么。
2. 定位本次改动涉及的接缝，说明接缝两侧分别是什么。
3. 举出一个当前的具体表现：角色、触发条件、可观察到的结果。
4. 无法从代码读出时（跨模块、线上行为、历史遗留）转入调研，材料落 `dev/research/`。

**变更影响**：基线改变后，第二节的要求失去原有参照——原不属于问题的现象可能变为问题；第六节的排除项须重新审视。

### 二、场景与要求

**目的**：逐场景列出要求，每条要求须能说明**什么情况算违反**，并给出一个具体的违反实例。无法给出实例的是愿望，不构成要求。

**依赖**：第一节（基线是要求的参照系）。

**可用手段**：

1. 穷举场景，一个场景对应一条链路，不合并——合并即丢失其差异。
2. 每个场景写成「谁在何处观察到什么」。
3. 逐条追问「什么情况算违反」，要求给出具体实例；给不出的当场改写或删除。
4. 统计其中否证性要求的条数：只有「存在某处 X」而无「只装 A、不装 B」的，须补齐。

**变更影响**：第三节的可行性（新增要求可能推翻「可做」的结论）；第四节（要求增多或加重可能需要分期）；第五节（新增要求必须可被验收）。

### 三、可行性结论与不可协商约束

**目的**：给出能否实现的结论、依据所在、已排除的路线，以及方案不得推翻的约束。结论须能说明「为何这条不行」，而非仅「据说不行」。方向性调研的全部结论都落在这里——他人如何解决、该路线是否成立、有无平台或协议硬限制、哪条路线已试过而不可行；方案阶段不重复这些内容，故此处缺漏没有第二处可补。

**依赖**：第二节（要求决定需要验证什么）；`dev/research/` 中的调研结论。

**可用手段**：

1. 从要求中提取「必须成立才做得成」的判断，逐条列为待验证项。
2. 先在**自身代码库**中寻找已解过同类问题的实例；无从查找时再向外参照——同层、同类、异形态，结论的可迁移性依次递减。
3. 以 `research` 取证：平台限制、协议行为、第三方能力、版本行为。
4. 记录已试过而不可行的路线及理由；不记录，方案阶段会重试一次。
5. 列出方案不得推翻的约束，逐条说明为何它是约束而非可选。

**变更影响**：第四节（不可行的路线不能排入分期）；第六节（被排除的路线须记一笔）；第二节（若某条要求不可行，该要求本身须修改）。

### 四、方案分期

**目的**：按期给出可观察的结果——每个分期结束时由谁观察到什么，一句话说得完。只写可观察结果，不写契约：契约属方案层，写入此处会使需求被实现形态锁定。

**依赖**：第三节（可行性）；第二节（要求的优先级决定各分期的先后）。

**可用手段**：

1. 找出「必须现在定」的分岔——只能选一个、选错须返工的那类决策。
2. 一个分岔对应一个分期。一个分期之内含两个分岔，说明尚未切开。
3. 为每个分期配一个可观察结果：做到什么程度、谁能看到。
4. 检查切分点是否落在「评审者可能接受 A 而拒绝 B」之处；切不开，说明它们本为一事。

**变更影响**：第五节（每个分期结果累加才构成整体完成，分期顺序变更须重算收口判据）。

### 五、收口判据

**目的**：给出 1 至 3 条产品级现象，作为整体完成的标志；不重复 plan 的技术判据。

**依赖**：第四节、第二节。

**可用手段**：

1. 将各分期的可观察结果累加，确认整体达成时呈现何种状态。
2. 收敛为 1 至 3 条现象，一条一句。
3. 检查：不查阅实现能否判断交付与否；不能则重写。

**变更影响**：无下游。若定稿时发现本节要大改，多半是第四节或第二节先变了，回头查一次再改。

### 六、范围外

**目的**：明确列出本次不做的事项，每条附带理由，并说明「现在不做的代价」是什么。

**依赖**：前五节——凡被排除者，均须在此有一句。

**可用手段**：

1. 汇集沟通过程中出现过的「以后再说」「顺手能做但不做」「这条不做」。
2. 每条写一句理由，再写一句不做的代价。
3. 检查是否混入了「想做而未敢提出」的内容——这类内容会在执行阶段转化为范围蔓延。

**变更影响**：无下游。

## 定稿

**交付之前过一次一致性检查。** 这些检查本应在每次改动时进行，列于此处的理由是：容易遗忘，而定稿前必须完成一次。

1. 第一节：基线写到可观察的层面？陈述的是问题而非症状？
2. 第二节：每条要求能给出一个具体的违反实例？否证性条数统计过——只有「存在某处 X」的已补成「只装 A、不装 B」？
3. 第三节：结论落在能做 / 不能做 / 有条件能做之一？已排除的路线写了理由？每条约束说明了为何是约束而非选择？
4. 第四节：一个分岔对应一个分期？每个分期有可观察结果？
5. 第五节：1 至 3 条？不查阅实现能判断交付与否？
6. 第六节：每条有不做的理由与代价？
7. 范围：是否仍在「一个可独立实施的子系统」之内；超出须拆。
8. 形式：占位符（TBD、TODO、「后续补充」、模板括号提示语、「待定」）是否清完？是否有句子可被读成两种意思？
9. 内部矛盾：是否有两节相互矛盾——尤其第四节的分期结果与第五节收口判据是否对应。
10. 越界与 YAGNI：是否出现具体文件路径、类名、依赖方向；是否存在无人要求过的功能或过度设计。

**第 2 条最容易违反。** 警惕仅含存在性检查的要求：「存在某处 X」能确认事实成立，不能否证「X 中混入了其他内容」。要否证须写成边界条件——「只装 A，不装 B」。统计否证性要求的条数，一条也没有时，验收只能证明「东西都在」，不能证明「没有多余的东西」。

对方评审使用同一套检查项，**只报会导致真实问题的项**（缺节、矛盾、歧义、无法被违反的要求）；措辞偏好、「某节不如另一节详尽」不构成阻塞理由。

### 门禁动作

交用户评审，等待明确回复。通过后依次完成三件事：`status` 由 `draft` 改为 `approved`；检查 `dev/PROJECT.md` 是否需要更新（判据：本需求是否改变了项目对外可见的能力或使用方式，纯内部重构不改）；运行一次 `workspace-status` 取得下一步。

**「通过」只针对当前这一份产物。** 想法被认可不等同于 spec 被认可，spec 被认可不等同于方案被认可——「他认可了想法，后面的应也算认可」是本节点最常见的误判。

## 不做的事

- **不写实现方案**。出现类名、文件路径、依赖指向，说明应转入方案阶段。
- **不分配编号**。使用状态查询给出的那一行。
- **不自行推进**。状态改写后须回到 `workspace-status`。
- **不在未获批准时将状态改为 `approved`**，也不写「已批准」这类自述——批准是用户的动作，记录在状态字段中即可。
