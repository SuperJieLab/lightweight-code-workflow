# 需求分析

这一步在需求提出之后、方案之前。它消除的风险是：需求到手时是多解的，而验收口径在动手前不可判定——等做到一半才发现两边理解不同，那时返工最贵。

它的产出是一份需求分析，读者是没参与这次对话的人：下一步写方案的人、几周后回来验收的人、几周后的你自己。

**产物写得浅，通常不是不认真，是生成时没有用力点。** 判据（指向正确、依据可核、结论明确）只能证明产出没有明显缺失，证明不了它够用——一份每节都填了、每条都有引用的文档可以全部通过，读起来仍然没有信息。决定深浅的是三件事：每节必须回答的问题有没有答、还不知道的事有没有被记下来、有没有人从没参与过的人的角度读过一遍。

## 输入与依赖

**前置状态**：`dev/` 已存在。没有就转 `workspace-init`，不要在别处建一套平行目录——两套并存之后，状态不知道该信哪个。

**编号来自外部**：Feature 目录的 `F<N>` 由 `workspace-status` 分配，本 skill 不取 max+1。

**开工先读**：

- `dev/README.md` 与 `dev/PROJECT.md` —— 这个工作区怎么用、项目现在是什么样。
- `dev/RULES.md` —— 既有工程规则与目录承诺表，写边界时拿它当基准。
- `dev/research/` 下与本需求相关的报告 —— 已有的证据不必重查，缺的按 `research` 补。

## 流程

六步有先后：不知道的事要先记下来，才谈得上补；证据补不齐，写出来的现状就是猜的。允许按缺口推进——哪一步最不清楚先补哪一步，但补完要回头确认前面没被推翻。

### 一、拆名词

需求通常是一句「让 A 能 B 这个 C」。拆解是把 A、B、C 逐个落下去：A 是哪一层、哪个入口；B 的触发条件、结果落在哪、失败时什么表现；C 是上游哪个类型、我们收到没有、存在哪。

落不下的名词就是这次的歧义，记进缺口清单，状态「待用户定」。落到两个地方，说明范围要拆成两个 Feature。

### 二、按条件补证据

三个方向，按命中的条件取用：

| 条件 | 走哪个方向 |
|---|---|
| 名词有歧义（一个词能指两个以上位置） | 顺着定义与调用找 |
| 有数据要改 | 从来源走到消费，每站都是改动点与回归点 |
| 影响面不明（不确定谁在用它） | 向上看谁依赖我，向下看我依赖谁 |

三类都不命中，在缺口清单里记一条「本次无需调研」并写明为什么。调研材料落 `dev/research/<主题>.md`，一份报告一组证据；文档只放结论与关键依据。

现状最容易被想当然：文件存在、注释这么写、有人提过，都推不出它正在被使用。这类错误要到事后才暴露，而那时已经改在上面了。

### 三、逐节策展

**至少对两节做**：背景与现状、需求拆解。这两节最容易写成一堆「是什么」。

每节分三步：先列候选（按复杂度 5-20 个可能写进去的点，编号）→ 交用户筛（留哪些、删哪些、合并哪些，删的附一句理由）→ 只写被留下的。

**策展完这一节就写这一节**，不要把所有节策展完再统一动笔——脱离刚筛完的清单去写，筛过的取舍就白做了。

为什么给数量下限：要求「写深一点」不可判，要求「先列 15 个点」可数。列到 15 个点时，会撞见其中几项其实不了解——那些直接进缺口清单。

策展交用户做，是因为取舍依赖优先级，而优先级在他脑子里。自己删会删掉不确定的、留下容易写的，正好删反。

### 四、写

按「每节必须有什么」逐节写。每节先答它该回答的那个问题，答完再展开；答不出就按那一行的缺项动作处理。

同一份文档只能用一条组织轴：按链路（新增了若干条可观察路径，一条一节）或按层（修正的是与既有结构的偏差，坐标系用对方的分层）。混轴的症状是有些节按模块写、有些节按时序写，读者以为分了两层。

每一节要能被上一节推出来。推不出的内容是并列，不是推进，读者会问「这跟上面什么关系」。

### 五、读者测试

写完后派一个**全新上下文**的子代理，交给它一句读者标准：

> 一个没参与本次对话、但有本领域经验的人，能否只凭这份文档写方案，不必回头问作者。

收回来的问题分三堆：文档已回答的（补进去）、次要的（自己定，在文档里标为你的决定）、只有用户能答的（一次性打包问，最重要在前）。**只允许一轮**——多轮会从补缺口滑向消耗耐心，且第二轮问的都是第一轮答过的。

读者卡住的段落，绝大多数是作者跳过的推理步骤。

### 六、定稿与交接

| 从 | 到 | 条件 |
|---|---|---|
| 不存在 | `draft` | 建好 `dev/features/F<N>-<主题>/`，写出第一版 |
| `draft` | `approved` | 退出判据全部成立，用户明确说这份可以了 |

**批准时同时定死 `phases`。** 改造步骤按依赖分组，一组一期，组数就是期数，写进文件头。它是这套流程判「这份 spec 做完没有」的唯一依据——没有它，一期交付完就会被当成整个 spec 完成。定了之后要改就是范围变更，走退档，不在执行中偷偷加一期。

交给下一步的是三样：每条要求的编号；每处改动牵动的面（用可命名的职责边界，不用类名与文件路径）；需要先定死的形状（改前与改后）。

## 每节必须有什么

模板有七节。第一列是它必须回答的问题，第二列缺了怎么办。

| 节 | 必须回答 | 缺了怎么办 |
|---|---|---|
| 基本诉求 | 要改什么；为什么这不是审美问题 | 说不出后者，说明还不该进这一步，回去问清为什么值得改 |
| 背景与现状 | 现在是什么形态；**为什么是这个形态**（约束来源）；改它会牵动谁 | 第二项答不出，记进缺口清单，不留空、不写「历史原因」 |
| 能不能做 | 三选一结论；依据指向具体报告或实测；已排除的路线与理由 | 依据指不到位置，标「判断未成立」，不写「基本可行」 |
| 需求拆解 | 每条能单独验收；有序列表，第 N 条即 SN；最后一条是做完之后仍须成立的性质 | 拆不出可验收的条目，说明模板第二节的现状还没弄清，回流程第二步 |
| 改造步骤 | 按依赖分组；每组一个可验收状态；改前改后给真实形态 | 分不出组，说明模板第四节的条目互不独立 |
| 收口判据 | 每条能被反面实例推翻 | 只能证明「东西都在」的，删掉重写 |
| 范围外 | 不做什么；理由；代价 | 写不出代价，说明这条其实想做，别放进范围外 |

「改造步骤」到形状为止：类、文件、依赖边留给 `plan-generation`。它不写「可单独验证」——那是方案里判据表的职责，写在 spec 里，执行时也只是照 plan 跑一遍。

## 缺口清单

这张表记的是**还不知道的**。它与「假设」不是一回事：假设是已经拍过板的（已决定、已核、暂不定），缺口是还在查的。混在一张表里，读者分不清哪些定了、哪些悬着。

| # | 问题 | 状态 | 影响哪条承诺 |
|---|---|---|---|
| 1 | 未读计数在服务端派生还是客户端计算 | 未查 | S2 |
| 2 | 多端同步失败由谁重试 | 待用户定 | S3 |
| 3 | 会话列表分页上限 | 查不到（服务端未设上限） | S1 |

四条规则：**状态四选一**（未查 / 查到 / 查不到 / 待用户定），除「查到」外都算未解；**绑不上任何承诺的问题删掉**，绑不上说明它不影响产出；**终止条件是清单为空**，空指每条都落到「查到」「用户已答」或「查不到且写清代价与在哪一步定」；**清单随文档一起交付**，它是下一轮的输入，也是「深不深」的可数证据。

## 边界取舍

**这条信息变了对端要不要跟着改。** 要，是承诺，留在这里；只有自己仓里换，留给下一步。

灰区问一句：这条变了，用户会不会说「这不是我要的」。会，是承诺；只会说「实现方式换了」，不是。

写的时候必然会做小取舍，比如选哪种粒度描述、先动哪一层。这不是越界，不必因此自我审查。真正要守的只有一条：**拿不准的不补全，标出来。** 补全之后，对方会以为那是自己的决定——这是这一步最难察觉的失败，因为它当时看起来像效率。

## 参考样式

`assets/spec.md.template` 按「诉求 → 背景与现状 → 能不能做以及边界 → 需求拆解 → 改造步骤 → 收口 → 范围外 → 假设 → 缺口」排。节可以合并、换序、增删；不能丢的是每节回答的那个问题——它写在模板每节的标题下面，与上面那张表一一对应。

## 退出判据

四条全部成立才算定稿，一条不成立就停在那一处：

**缺口清单为空。** 每条已落到「查到」「用户已答」或「查不到且写清代价与在哪一步定」。

**每节都答出了它该回答的问题。** 逐节对照「每节必须有什么」，答不出的那一节要么补，要么合并——不能靠改措辞过关。

**删节测试通过。** 逐节问「删掉这一节，读者会得出错误结论吗」。答「不会」的，说明这节是废话，合并或删掉后重新测。

**读者测试没有新缺口。** 全新上下文的读者能据此写方案，且没有暴露出缺口清单里没记过的问题。

批准是用户的动作，不要自己写「已批准」。想法被认可不等于文档被认可，文档被认可不等于方案被认可。

## 不做的事

想法与对策成对写，左边是会上来的那句话，右边是替代动作。

| 念头 | 现实 | 替代动作 |
|---|---|---|
| 「这几节模板没要求细写，先略过」 | 模板是下限不是上限，略过的节正是要写的地方 | 写一句「本节不适用，因为…」，再往下走 |
| 「先写完，回头再补成因」 | 回头不会补。成因是这一节唯一要求判断的部分 | 写不出就记进缺口清单，不要留空 |
| 「这处我填个合理默认值」 | 没被听见的默认值，等于没被否决过 | 记进缺口清单，标「待用户定」 |
| 「用户说先这样，够用了」 | 批准覆盖的是他看到的东西，他看到的是草稿 | 先跑读者测试，再问批准 |
| 「基本可行，细节到时候再说」 | 下一步无法据此决定要不要开始 | 三选一，附依据；说不清就标「判断未成立」 |

两条不属于上面这些念头，单独列：

- **不自己取编号。** 用 `workspace-status` 给的那一行；并行需求会撞号，撞号之后没有一处能裁决。
- **不在本节点消化承诺变更。** 已 `approved` 的承诺要改，是重开（`status` 退回 `draft` 并连带 plan 退回），不是编辑。
