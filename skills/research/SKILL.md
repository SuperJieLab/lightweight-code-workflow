# 调研 —— 查清现在是什么样

> 结论要能直接当判断用。一次调研固定产出一份报告。
> 调研回答「现在是什么样」，**不回答「该怎么办」**——后者是决定，不是事实。

## 什么时候用

两条入口，任一条成立就该查：

- **主动**：用户说「查一下 / 调研一下 / 这个能不能做 / 业界怎么做」。
- **被动**：某条断言拿不出可追溯的依据，且属于三种之一：
  - 涉及当前系统怎么运转，却无法从本次改动的代码看出（跨模块、线上行为、历史遗留）；
  - 涉及能不能做，而有未验证的外部约束（第三方能力、协议、平台限制、版本行为）；
  - 依赖某条路已排除，而排除理由来自记忆。

一条都不成立就别查。无触发而调研，是用工作量替代判断；查完的结论也会因为没有用处而迅速过期。

## 先拆问题：要回答什么

原始诉求通常是一句话，先把它拆成几条**能判定真假**的问题（通常一到三条），再动手：

- 一个问题一条，不合并——合并会丢掉各自的证据要求。
- 每条标注「它会被哪个决定用到」。标不出的删掉，否则查的是好奇心不是依据。
- 一个问题常常两类材料都要：比如「这个方案可行吗」，既要平台限制（外部），也要现有实现怎么走（仓库内）。此时不是做两次调研，是同一次调研的两组证据。

**停：拆完先报一次。** 把这几条问题连同「各自服务哪个决定」一起报给用户，等他点头再开查。理由不是礼节——一次调研要读十几个文件、跑几条命令，方向错了这些全白费，而三条问题的确认成本只有一条消息。

用户改了问题就重拆，不要在已确认的清单外顺手多查。

## 两类材料

| 类别 | 包含什么 | 一手来源在哪 |
|---|---|---|
| **外部事实** | 平台限制、协议行为、第三方能力、竞品做法、版本变更 | 官方文档、源码、规范、changelog、官方 issue |
| **本仓库现状** | 现有实现怎么运转、谁在调用、模块边界在哪、有没有人做过同类东西 | 代码、配置、提交历史、运行输出 |

两类都要能落到可追溯的位置：外部落到链接或原文，内部落到 `文件:行号`。

## 外部事实怎么查

1. **按权威性排来源**：官方文档 / 源码 / 规范 / changelog ＞ 官方 issue ＞ 同类产品的实现 ＞ 社区讨论 ＞ 二手文章。低权威来源只用来找线索，不用来定结论。
2. **读源码优先于读注释**：注释解释的多是「为什么」，不总是「怎么做的」；两者冲突以代码为准。依赖方的行为去它的仓库查 tag 之间的 diff，比读注释可靠。
3. **记下版本与时点**：外部事实会随版本失效。写下结论所依据的版本号，重用时先确认它现在仍成立。
4. **区分「没写」与「没有」**：文档没提到某个行为，不等于该行为不存在；要判断不存在，得在源码或实测里找。

## 本仓库现状怎么查

1. **先找已解过此题的实例**：同一个系统里做过同类事的模块，数据与约束最接近，差异可定位。直接看它是怎么解的，比通读全部代码快。
2. **先定位，再走通**：从版本控制拿文件清单（它已排除构建产物与被忽略的目录），用符号名或关键串搜，命中后只读附近的行窗口，再沿调用链走到能说清「谁调用谁、状态存放于何处、失败时如何返回」。通读整个仓库既慢，又会让注意力摊平。行号是搜出来的，不是推出来的——凭印象给出一个，几乎必偏。
3. **读大文件要带元信息**：总行数、这次读了哪一段、是否被截断。截断了就缩窄范围重读，不要拿半截内容当全文——后半段常常正好装着反例。
4. **用运行结果验证推断**：读代码容易漏掉配置、路由、动态注册。跑一条命令、看一次日志。日志很长就看全量，不要头尾各截几行——被截掉的那段往往正是结论所在。
5. **写下成立前提**：这个现状在什么条件下才成立（特定配置、特定版本、特定部署形态），前提变了结论就废。

## 查不到的时候

三种情形，处置不同。共同点是不许把「查不到」写成一条结论：

| 情形 | 怎么处置 |
|---|---|
| **外部来源不可达**（文档下线、仓库私有、无法联网） | 降到次一级权威来源，并在依据里写明「原定来源不可达，退到 X」。仍落不到链接的，标置信度并写清低在哪 |
| **旧报告与本次结论冲突** | 两份都留着：在原报告上补本次结论，写明冲突点与各自的依据时点。不静默覆盖旧结论——它当时可能是对的，是版本变了 |
| **`dev/` 不存在**（新仓库或未初始化） | 先跑 `workspace-init` 建骨架再落报告；不把报告写到 `dev/` 之外，那样下一个人找不到 |

## 报告：固定产出

一次调研一份，落 `dev/research/<主题>.md`，按内容命名、不带日期——它讲的是事实，别人也会来查。内容多少都一样出一份：对话里的结论不算交付，理由见「不做的事」。

同一主题再查时，在原报告上补并注明复核时间，不另建第二份——同一个事实有两个文件，读的人不知道该信哪个。

### 报告有四项

| 项 | 写什么 | 达标的样子 |
|---|---|---|
| **问题** | 这次要回答什么 | 每条能判定真假；每条说得出被哪个决定用到 |
| **结论** | 每条问题对应一句判断 | 能直接拿去当判断用，不留「可能」「大概」；一条问题一条结论，不合并 |
| **依据** | 这个判断从哪来 | 落到链接、`文件:行号` 或命令输出；落不到的标了置信度并写明低在哪 |
| **适用范围** | 这个结论在什么范围内成立 | 说得出至少一条具体条件（特定版本、配置、部署形态），或明确写「稳定事实」 |

四项缺任一项，报告不成立：缺结论是没查完，缺依据是不能被核对，缺适用范围是读的人不知道它能用到哪。

### 依据怎么写

- 引外部资料给来源与链接；只能用二手来源时，标明是二手。
- 引本仓库代码给 `文件:行号`，**引用前打开那几行确认**——行号指向相邻逻辑是最常见的假引用。
- 写在文档里的结论只是当时的采样。读的人重用它之前要自己确认一次，报告不代替这个确认。

### 自查

写完拿四项表的「达标的样子」逐项对照，答「否」的那项回去补，补完再对照，直到四项全过。此外单加一问：

- 有没有哪条结论其实还是「两种可能都有」——那说明问题没查完。

四项全过即完成，不必再回头「确认一下」：反复重查换不来新信息，只会把报告写长。

## 不做的事

- **不写方案，不做技术决策。**「所以我们应该用 A」是决定，不是调研结论。
- **不抄文档原文大段。** 抄来的段落六个月后没人知道它在讲哪一版。
- **不在对话里给结论就算交差。** 没有报告，结论只活在这一次会话里，下一个人还得重查。
- **不在没拆问题前开查。** 边查边想会得到一堆互不对齐的碎片，最后仍然说不清「所以呢」。
- **不为再确认反复下钻。** 一条结论的证据够了就停；够的判据是能被核实，不是能被反复确认。
