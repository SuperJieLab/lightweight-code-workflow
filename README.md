# 轻量代码工作流 · Lightweight Code Workflow

一套给 AI 编码代理用的开发流程：把「提承诺 → 写方案 → 执行 → 复核 → 精简 → 交付」拆成十个可单独调用的 skill，状态存在文件头，流程知识只存一处。

不是提示词合集，是一套有状态机、有判据、有退出条件的作业规范。

---

## 它解决什么

让 AI 写代码，失败通常不发生在「代码写不出来」，而发生在这几处：

- **做偏了没人发现。** 当初承诺的是 A，中途做成了 A'，到交付时才发现，而那时返工成本最高。
- **状态活在对话里。** 换一次会话、换一个人接手，就得从头问一遍「现在做到哪了」。
- **复核只有自审。** 自己审自己，等于没审——审查者手里的信息和实现者一样，看不出自己漏了什么。
- **旧代码没人清。** 需求换了，旧链路还挂着，静态工具查不出来（链路内部还在互相引用，只是入口断了）。

这套流程对每一条都有对应的机制，而不是靠提醒。

## 核心设计

**状态只写在文件头。** `spec.md` 与每份 `plan.md` 的 front-matter 是唯一真实数据源，任何索引表都不存状态。两份状态迟早不一致，而不一致时没人知道该信哪份。

**一个承诺一条判据。** spec 里每条承诺都要能指到一条可执行的判据（命令、期望输出、可勾选的现象）。指不到的承诺不算承诺。

**复核分两层，对照物不同。** 一层看代码本身有没有病（并发、内存、边界、错误处理），对照物是语言规范；一层看实现有没有兑现方案（结构、契约、归属、判据覆盖），对照物是 plan，由独立子代理执行。两层不合并——合并之后，第二层会去审 plan 的错，而它审不出来。

**调研固定产出一份报告。** 外部事实与本仓库现状都落在 `dev/research/` 同一份文件里，写清结论、依据、以及**结论在什么条件下不成立**。

**流程要对 agent 可见。** 初始化时把一段桥接文案写进项目记忆，否则 agent 不知道这个项目用了哪套流程，`dev/` 建好了也不会被读。

## 十个 skill

| 层 | skill | 做什么 |
|---|---|---|
| 工作区 | `workspace-init` | 铺骨架（四份文档、两个目录），写桥接块 |
| 工作区 | `workspace-status` | 读状态、报矛盾、给下一步 |
| 节点 | `spec-generation` | 把需求拆解成一份可判断的分析：现状、目标、边界、改造思路 |
| 节点 | `plan-generation` | 把承诺变成能照着执行的方案 |
| 节点 | `tdd` | 逐项做，红-绿循环，一件一提交 |
| 节点 | `code-review` | 两层复核，阻塞级问题不修不得继续 |
| 节点 | `code-slim-audit` | 清死代码，判「还有没有人在用」 |
| 节点 | `spec-verify` | 核验每条承诺兑现了没有，关闭需求 |
| 能力 | `research` | 查清一件事现在是什么样，产出一份报告 |
| 能力 | `grill-me` | 用追问把模糊想法问到清晰 |

「节点」有独立产物、有退出判据、改状态；「能力」没有状态，任何节点都可以调用。

## 怎么用

**一、把 `skills/` 放进去。** WorkBuddy 放 `~/.workbuddy/skills/`（全局）或 `<项目>/.workbuddy/skills/`（项目级）。Claude Code 等支持 `SKILL.md` 约定的工具同理。

**二、初始化。** 在仓库根说「初始化工作区」。它会建 `dev/` 骨架并把桥接块写进 `.workbuddy/memory/MEMORY.md`。

**三、开始。** 说「我要做 X」，从 spec 开始；或者不知道下一步做什么时说「下一步」，由 `workspace-status` 告诉你。

之后每个节点做完会自己推进状态，再问你一次下一步。你不需要记流程——流程只在 `workspace-status` 里。

## 目录结构

```
dev/                          工作区产物
├── README.md                 这个工作区怎么用
├── PROJECT.md                项目现在是什么样
├── RULES.md                  工程规则与目录承诺
├── ISSUES.md                 未结事项
├── research/                 调研报告，一个主题一份
└── features/
    └── F12-<主题>/
        ├── spec.md           需求分析：现状、目标、边界、改造思路
        ├── plans/            一个分期一份实现方案
        └── checks/           复核与精简的快照，带日期
```

## 设计与取舍

`WORKFLOW-DESIGN.md` 是设计依据：每一条决策都带判据与反例，以及**被否决的方案和否决理由**。比如为什么不做「调研独立成节点」，为什么取消「research / evidence 两个目录」，为什么 workspace-status 不替用户启动下一个 skill。

想知道某个设计为什么长这样，答案在那里；想知道怎么用，看 `skills/README.md`（每份 skill 的构成规范、结构纪律、依赖纪律）。

## 适用范围

**适合**：需要长期维护、有多期交付、一个人或小团队与 AI 协作的项目。需求要能被写成「可判定的承诺」，否则这套流程的收益会打折。

**不适合**：一次性脚本、探索性原型、需求本身还没想清楚的时候。后者的正确动作是先把需求聊清楚（`grill-me` 与 `spec-generation`），不是跑完整流程。
