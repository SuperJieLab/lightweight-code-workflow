## 三、二轮：`covers` 机制的五个问题

今早从插件反向同步进来的那套改动思路是对的——一份 spec 分几期交付是常态，`delivered` 该表示「全部承诺兑现」而不是「现有 plan 都做完了」。但它只接了判定端，没接产出端，且把判断放在了错误的层。

**一、`covers` 在自己所属的 skill 里出现 0 次。** 字段只在 `plan.md.template` 里，`plan-generation/SKILL.md` 一个字没提。

**二、模板默认值 `covers: []` 是误报开关。** `covers_of` 对 `[]` 返回空集合而非 `None`，绕过「全都未声明就不判」的兼容分支。实跑：plan 已 `closed`、`covers` 留空 → `待补方案`。与第一条叠加，新项目开箱即错。

**三、阶段名不一致。** 转移表写「还有承诺没有 plan」，`status.py` 输出「待补方案」。昨夜刚统一过「待核验 / 待交付」，几小时就回来了。

**四、矛盾检查少一条。** 文档六条，脚本七条。

**五、一个「承诺没做」有三个去处。** 覆盖检查回 R2，三态表说「写进遗留还是退回 R1」。

这五条二轮时都修了。但修完之后更根本的问题显出来：这套机制的六个活动部件（新字段、集合运算、两份事实、新阶段名、新矛盾项、跨文件人工一致性）里，没有一个是必要的——复杂是因为判断被放在了 plan 层，而「整体做完没有」是 spec 层的问题。

## 四、三轮：换成 spec 声明期数

`covers` 全套删除，改为：

```yaml
# spec.md front-matter
phases: 3          # 本 spec 共几期；不写 = 1
```

判定从集合运算变成按序号扫描——第 1..phases 期里找第一个未完成的，plan 不存在也算未完成。

| 部件 | `covers` 方案 | 现在 |
|---|---|---|
| spec 字段 | 无 | +1（`phases`） |
| plan 字段 | +1（`covers`） | 0 |
| 脚本函数 | +3 | −3 |
| 阶段名 | +1（待补方案） | 0（并入待写方案） |
| 矛盾项 | +1 | +1（期号超过 `phases`） |
| 人工维护的不变式 | 两处事实必须一致 | 无 |

配套定的三条规则：

- **期数在 spec 批准时定死**，按改造步骤的依赖分组数。要改就是范围变更，走退档。
- **不加期。** 执行中发现还得多一期，不新建 `plan-N+1`，多出来的事塞进当前期；真需要多一期改 spec 走退档。
- **追加任务用加号。** `T4+1` 表示 T4 之后追加的，`+` 与点号分工（点号留给「一个任务拆成几个子步骤」）。旧编号不动。加任务归三层分流的第二层，前置判据是「会不会改变某条承诺的兑现方式」。

另外钉了一处：**plan 的执行结果在 `closed` 时定稿**，不在 `done`。复核与精简都可能让代码再变一次，`done` 时写的总结会变成过期快照，而 `spec-verify` 读的正是它。

回归六项全过：`phases: 3` 只 close 第 1 期 → 待写方案第 2 期；第 2 期 abandoned → 待交付；`phases: 1` → 待交付；期号 1、3 → 报断号；`phases: 2` 第 2 期 executing → 执行中；plan 期号 4 而 `phases: 3` → 报「多加了一期」。
